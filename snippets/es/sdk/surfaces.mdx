**Un paquete, dos superficies.** `comfy-sdk` (PyPI) y `@comfyorg/sdk` (npm) incluyen dos clientes que hablan con dos servicios diferentes. Los nombres de los métodos se repiten entre ambos (`run`, `submit`, `events`) y significan cosas distintas en cada uno, así que revisa qué cliente construye un fragmento de código antes de copiarlo.

| Superficie | Qué hace | Cómo accedes a ella | URL base | Autenticación |
|---|---|---|---|---|
| **[Comfy Router](/es/development/comfy-router/quickstart)** | Llama a un modelo socio (FLUX, Veo, Gemini, Kling) con el cuerpo de solicitud propio de ese proveedor y devuelve su respuesta nativa | Python: `client.models` en un `Comfy()`. TypeScript: `comfy.models` en el espacio de nombres `comfy` a nivel de módulo | `https://api.comfy.org`, ruta `/v2/models/{provider}/{model}` | `COMFY_API_KEY`, o `comfy.config({ credentials })` |
| **[Comfy Cloud y Comfy API v2](/es/development/api-development/sdks)** | Ejecuta un flujo de trabajo de ComfyUI en formato API de principio a fin: sube recursos, envía el gráfico, sigue la tarea y descarga las salidas | `Comfy(api_key=...)` / `new Comfy({ apiKey })`, luego `client.workflows`, `client.assets`, `client.jobs` | `https://cloud.comfy.org` de forma predeterminada, o lo que indique `COMFY_BASE_URL` | `api_key` / `apiKey` en el constructor |

Ninguna superficie envuelve a la otra, y una misma clave API creada en [tu espacio de trabajo de Comfy](https://platform.comfy.org/profile/api-keys) funciona para ambas.

<Note>
  Los dos lenguajes exponen la superficie del Router de manera distinta. En Python, `Comfy()` incluye ambas: `client.models.run(...)` para el Router y `client.workflows` / `client.assets` / `client.jobs` para Cloud. En TypeScript son exportaciones separadas con nombres deliberadamente similares: `comfy` (en minúsculas, el espacio de nombres a nivel de módulo) contiene `comfy.models`, mientras que `Comfy` (la clase) es el cliente de Cloud y no tiene `.models`.
</Note>
