Sobald ComfyUI [irgendwo bereitgestellt](/de/development/deploy/overview) ist, führt Ihre Anwendung dort Workflows aus: einen Workflow absenden, auf die Ausführung warten, die Ausgänge herunterladen. Diese Seite zeigt, welcher Client für welche Bereitstellung verwendet wird.

## Hier starten: die Comfy SDKs

Für eine neue Integration verwenden Sie die offiziellen **Comfy SDKs** (Python und TypeScript) und die [Comfy API v2](/api-reference/v2/overview), die sie aufrufen. Derselbe Code funktioniert mit jedem Bereitstellungsziel; nur die Basis-URL ändert sich.

<Card title="Comfy SDKs" icon="code" href="/de/development/api-development/sdks">
  Installieren Sie ein SDK, um Workflows aus Python oder TypeScript abzusenden und Ausgänge herunterzuladen.
</Card>

## Was womit funktioniert

| Bereitstellung | Comfy SDKs / API v2 | Hinweise |
|---|---|---|
| **Comfy API-Bereitstellung** | Ja | Richten Sie `COMFY_BASE_URL` auf `https://<deployment>.run.comfy.app` und Ihren API-Schlüssel aus |
| **Comfy Cloud** | Ja | Die standardmäßige Basis-URL. Erfordert einen API-Schlüssel und ein kostenpflichtiges Abonnement |
| **Selbst gehostet** | Ja, über den [API-Proxy](/de/development/comfyui-server/api-proxy) | Ein kleiner Dienst neben ComfyUI stellt die v2-API bereit |

Selbst gehostete Instanzen können das SDK auch ganz überspringen und die reine [ComfyUI Server API](/development/comfyui-server/comms_overview) (REST + WebSocket) verwenden. Sie stellt die vollständige lokale Oberfläche bereit, einschließlich Warteschlange und Node-Info, gibt aber keine Kompatibilitätsgarantie über Releases hinweg.

## Welche API sollten Sie verwenden?

| | Comfy API v2 + SDKs | v1 Cloud API | ComfyUI Server API |
|---|---|---|---|
| **Wo sie läuft** | Comfy API-Bereitstellungen, Comfy Cloud oder selbst gehostet über den API Proxy | Nur Comfy Cloud | Nur selbst gehostet |
| **Kompatibilität** | Versioniert, innerhalb von v2 nur additive Änderungen | Veraltet, Änderungen ohne Ankündigung möglich | Keine Garantie über Releases hinweg |
| **Authentifizierung** | `Authorization: Bearer` bei Comfy Cloud und Comfy API-Bereitstellungen. Selbst gehostet: standardmäßig keiner, optional ein statischer Bearer-Token | `X-API-Key`-Header (Comfy-Cloud-Konto) | Keiner (lokal) oder API-Schlüssel für Partner-Nodes |
| **Offizielle Clients** | Python- und TypeScript-SDKs | Keine, Aufruf über HTTP | Keine, Aufruf über HTTP |
| **Protokoll** | REST + SSE | REST + WebSocket | REST + WebSocket |
| **Umfang** | Workflow ausführen und Ergebnisse abrufen | Vollständige Cloud-Oberfläche, einschließlich Modelle und Konto | Vollständige lokale Oberfläche, einschließlich Warteschlange und Node-Info |
| **Am besten geeignet für** | Neue Integrationen, die weiterhin funktionieren sollen | Bestehende Integrationen und Cloud-Funktionen, die v2 noch nicht abdeckt | Volle Kontrolle, eigene Tools für Ihre eigene Instanz |

Alle akzeptieren dasselbe Workflow-Format ([API-Format](/de/development/api-development/workflow-api-format)), sodass Sie Workflows lokal entwickeln und testen und ohne Änderungen in eine andere Bereitstellung verschieben können.

## Voraussetzungen

- Einen [API-Schlüssel](/de/development/api-development/getting-an-api-key) für alles, was Comfy Cloud, eine Comfy API-Bereitstellung oder Partner-Nodes betrifft. Ein rein lokales ComfyUI benötigt keinen.
- Einen im [API-Format](/de/development/api-development/workflow-api-format) exportierten Workflow.
