## Anbieter, die das Modell bereitstellen

Dieses Modell wird direkt von Comfy Router bereitgestellt, sofern die Anfrage keinen anderen Anbieter nennt. Die folgenden Anbieter stellen es ebenfalls bereit, über denselben Endpunkt und mit derselben Modell-ID, ausgewählt über den Query-Parameter `model_provider`.

- **Comfy** (Standard): `POST https://api.comfy.org/v2/models/vertexai/gemini-3-pro-image`
- **fal**, als `fal/fal-nano-banana-pro`: `POST https://api.comfy.org/v2/models/vertexai/gemini-3-pro-image?model_provider=fal`
- **MiniMax**, als `minimax/minimax-nano-banana-pro`: `POST https://api.comfy.org/v2/models/vertexai/gemini-3-pro-image?model_provider=minimax`
- **Pika**, als `pika/pika-nano-banana-pro`: `POST https://api.comfy.org/v2/models/vertexai/gemini-3-pro-image?model_provider=pika`
- **Runware**, als `runware/runware-nano-banana-pro`: `POST https://api.comfy.org/v2/models/vertexai/gemini-3-pro-image?model_provider=runware`
- **WaveSpeed**, als `wavespeed/wavespeed-nano-banana-pro`: `POST https://api.comfy.org/v2/models/vertexai/gemini-3-pro-image?model_provider=wavespeed`

`strict_mode` ist standardmäßig `false`, daher übersetzt Router den auf dieser Seite dokumentierten nativen Request-Body in das eigene Schema des Anbieters und übersetzt die Antwort zurück. Siehe [`model_provider`, `strict_mode` und `fallback_provider`](/de/development/comfy-router/reference#post-v2modelsprovidermodel) in der API-Referenz und [Anbieter, die das Modell bereitstellen](/de/development/comfy-router/providers) für jedes Modell, das auf diese Weise geroutet wird.

### Die Parts lesen

Standardmäßig enthalten generierte Bild-Parts base64-Bytes in `inlineData.data` und einen Medientyp in `inlineData.mimeType`. Dekodieren Sie die Bytes und speichern Sie sie in einer Datei. Mit `uploadImagesToStorage: true` verwenden hochgeladene Bilder stattdessen `fileData.fileUri` für eine signierte URL und `fileData.mimeType` für den Medientyp. Laden Sie diese Bilder herunter, bevor die URLs ablaufen, also 24 Stunden nach ihrer Erstellung.

**`fileData` kann in einer Antwort auftauchen, die es gar nicht angefordert hat.** Die beiden Formen gelten pro Part, nicht pro Antwort: Ist `uploadImagesToStorage: true` gesetzt, bleibt ein Bild, dessen Upload fehlschlägt, als `inlineData` erhalten, sodass eine Antwort beide Formen mischen kann. Verzweigen Sie danach, welcher Schlüssel vorhanden ist, und nicht danach, was Sie angefordert haben. Der einzige Fall, der nicht eintreten kann, ist der umgekehrte: Ist das Feld nicht gesetzt oder `false`, kommt jedes generierte Bild als `inlineData` zurück, und es wird kein `fileData`-Bild-Part erzeugt. Text-Parts können ebenfalls auftauchen, und das Bild ist nicht zwingend der erste Part. Wählen Sie einen Part daher über das Feld aus, das Sie benötigen, und nicht über den Index. Der Pfad `candidates[0].content.parts[0].inlineData.data` in den Quickstart-Beispielen oben liest den einzigen Inline-Part der Beispielantwort auf dieser Seite; prüfen Sie bei einer echten Antwort `parts` auf den gewünschten Schlüssel, statt Position 0 zu indizieren.

**`thoughtSignature` ist ebenfalls ein Part-Feld, und es ist groß.** Ein Part kann `thoughtSignature` tragen, eine undurchsichtige base64-Signatur der Denkweise des Modells, die existiert, damit der Gedanke in einer späteren Anfrage erneut abgespielt werden kann. Im oben generierten Schema fehlt es, weil dieses dem Request/Response-Dokument folgt, das Router veröffentlicht. Auf echten Antworten gemessen liegt es bei etwa 1 bis 2 MB pro Part, vergleichbar mit dem Bild selbst. Es lohnt sich daher, dafür Budget einzuplanen oder es explizit zu verwerfen, wenn Sie Antworten protokollieren, sie über eine serverlose Funktion weiterleiten oder sie speichern.

### `imageSize` ist eine Klasse, keine Breite

`generationConfig.imageConfig.imageSize` akzeptiert `1K`, `2K` oder `4K`, und jede Stufe verdoppelt beide Kanten, statt eine Breite festzulegen. Eine 16:9-Anfrage maß 1376x768 bei etwa 1.35 MB unter `1K` und 2752x1536 bei etwa 5.6 MB unter `2K`: dasselbe Seitenverhältnis, viermal so viele Pixel und rund viermal so viele Bytes. `2K` bedeutet also nicht ein Bild mit 2048 Pixel Breite, und wenn Sie einen Upload-Pfad, ein Limit für den Antwort-Body oder einen Storage-Bucket gegen `2K` dimensionieren, als wäre es eine Breite, provisionieren Sie ihn um etwa das Vierfache zu klein.

### Referenzen verketten

Wenn Sie ein zuvor generiertes Bild direkt wieder einspeisen, erhalten Sie einen neuen Kamera-Winkel auf dasselbe Motiv. Eine Folge von Aufnahmen einer Szene ist daher eine Kette von Aufrufen und nicht ein Prompt, der alles auf einmal beschreiben muss. Architektur, Materialien und Beleuchtung bleiben oft über eine Kette hinweg erhalten, aber das Modell garantiert es nicht. Behandeln Sie Kontinuität als ein wahrscheinliches Ergebnis, das Sie prüfen sollten, und nicht als eine Eigenschaft, auf die Sie sich verlassen können.

Senden Sie das Bild in der Form zurück, die die vorherige Antwort verwendet hat. Nehmen Sie bei einem `inlineData`-Part die base64-Bytes aus `inlineData.data` und senden Sie sie unverändert als `inlineData`, wie unten gezeigt. Bei einem Part, der unter `uploadImagesToStorage: true` als `fileData` zurückkam, senden Sie stattdessen `fileData.fileUri` und `fileData.mimeType` als `fileData`-Part, solange die signierte URL noch gültig ist; ein erneutes Hochladen der Bytes als `inlineData` funktioniert ebenfalls und läuft nicht ab. Fordern Sie dann die gewünschte Änderung an:

```json
{
  "contents": [
    {
      "role": "user",
      "parts": [
        {
          "inlineData": {
            "mimeType": "image/png",
            "data": "<the base64 from candidates[0].content.parts[].inlineData.data of the previous response>"
          }
        },
        { "text": "the same room, viewed from the opposite corner at eye level" }
      ]
    }
  ],
  "generationConfig": {
    "responseModalities": ["IMAGE"],
    "imageConfig": { "aspectRatio": "16:9" }
  }
}
```

Jeder Aufruf ist unabhängig. Übergeben Sie daher das Bild, auf dem Sie aufbauen möchten, statt sich auf den Gesprächsverlauf zu verlassen. Achten Sie beim Verketten auf die Größe des Request-Bodys: Das Inline-Bild zählt gegen das [Limit für den Request-Body](/de/development/comfy-router/limitations#request-bodies-are-capped) von Router, und ein `2K`-Bild hat etwa viermal so viele Bytes wie ein `1K`-Bild.
