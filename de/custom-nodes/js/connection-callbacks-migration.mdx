Callback-Signaturen haben sich nicht geändert. `onConnectionsChange`, `onConnectInput`, `onConnectOutput` und `onBeforeConnectInput` behalten ihre bestehenden Argumente und ihr Timing. Zu Änderungen an der Verbindungsregistrierung und an der `LinkNetwork`-API siehe [Migration der Verbindungsregistrierung](/custom-nodes/js/link-registration-migration).

## Auf SubgraphIO an Subgraph-Grenzen prüfen

An einer Subgraph-Grenze (einem `SubgraphInput` oder `SubgraphOutput`) wird
`onConnectionsChange` weiterhin ausgelöst, doch das fünfte Argument ist ein
`SubgraphIO` und nicht der übliche `INodeInputSlot`/`INodeOutputSlot`. Prüfen
Sie darauf, bevor Sie das Argument als normalen Slot behandeln. Die Guards
`isSubgraphInput` und `isSubgraphOutput` des Frontends sind für Erweiterungen
nicht verfügbar. Prüfen Sie deshalb auf das Array `linkIds` und den Node
`parent`, die jedes `SubgraphIO` besitzt und Node-Slots nicht:

```js
function isSubgraphIO(slot) {
  return slot != null && Array.isArray(slot.linkIds) && 'parent' in slot
}

nodeType.prototype.onConnectionsChange = function (
  type,
  index,
  isConnected,
  link,
  slotOrIO
) {
  if (isSubgraphIO(slotOrIO)) return
  // slotOrIO ist INodeInputSlot | INodeOutputSlot
}
```

## Node-Lebenszyklusereignisse mit graph.events abonnieren

`graph.events` löst `node:added`, `node:before-removed` und `node:removed` aus. Verwenden Sie diese, wenn mehr als ein Teil Ihrer Erweiterung beobachten muss, wie ein Node hinzugefügt oder entfernt wird:

```ts
graph.events.addEventListener('node:added', (e) => {
  console.log('added', e.detail.node.id)
})
```

`node.onAdded`, `node.onRemoved` und die Single-Slot-Varianten `graph.onNodeAdded`/`graph.onNodeRemoved` funktionieren weiterhin, aber das Zuweisen von `graph.onNodeAdded` ersetzt jeden vorhandenen Handler: Ein zweiter Abonnent verdrängt den ersten stillschweigend. Bevorzugen Sie `graph.events`, es sei denn, Sie müssen beim Hinzufügen oder Entfernen ein Veto einlegen oder Werte verändern. Für connect/disconnect gibt es kein Äquivalent für mehrere Abonnenten; `onConnectionsChange` ist weiterhin der einzige Hook pro Verbindung.

## Beim Entfernen eines Nodes werden Callbacks in dieser Reihenfolge ausgelöst (teilweise getestet)

Das Entfernen eines Nodes löst in dieser Reihenfolge aus:

1. `node:before-removed`: Der Node ist noch vollständig eingebunden.
2. `onConnectionsChange(..., false, ...)` am entfernten Node und an jedem
   verbundenen Partner, während der entfernte Node noch im Graph liegt.
3. `node.onRemoved()`: `node.graph` ist noch gesetzt.
4. Der Node löst sich von den Graph-Indizes und Stores; `node.graph` wird
   `null`.
5. `onNodeRemoved(node)`, dann `node:removed`; beide sehen einen bereits
   abgelösten Node.

Tests decken `node:before-removed → node.onRemoved() → onNodeRemoved(node)` ab
und prüfen separat, dass `node:removed` einen abgelösten Node sieht. Die
vollständige Sequenz einschließlich Schritt 2 ist aus der Quelle abgeleitet und
nicht durch einen durchgängigen Test garantiert.

Um den entfernten Node aus dem `onConnectionsChange`-Handler eines Partners
heraus zu ermitteln, tun Sie das in Schritt 2 über `graph.getNodeById()`. Bei
`node:removed` ist der Node bereits weg.

## Beim Laden eines Workflows werden Peer-Nodes aufgelöst, bevor onConnectionsChange ausgeführt wird

`graph.configure()` erstellt jeden Node im Workflow, bevor das eigene `configure()` eines Nodes läuft, und löst `onConnectionsChange` für die wiederhergestellten Verbindungen aus. Wenn Ihr `onConnectionsChange`-Callback also während des Ladens ausgelöst wird, existiert jeder Peer-Node bereits und seine Verbindung ist schon registriert. Daher liefern `graph.getNodeById()` und Abfragen von Verbindungen aus diesem Callback heraus korrekte Ergebnisse.

## Der Import von API-Prompts verbindet aufgelöste Eingaben nicht erneut

`app.loadApiJson()` verbindet jede auflösbare Eingabe, ohne einen zweiten Durchlauf zum Trennen und erneuten Verbinden auszuführen. Erweiterungen sollten sich beim Import von API-Prompts nicht auf doppelte `onConnectionsChange`-Benachrichtigungen verlassen. Lassen Sie jeden Verbindungs-Handler seine Arbeit bereits bei der ersten Benachrichtigung erledigen; verschieben Sie Arbeiten, die den vollständig importierten Graphen erfordern, nach `afterConfigureGraph` oder `afterLoadGraph`.

Eingaben, deren Quell-Ausgang oder Ziel-Slot noch nicht existiert, werden erneut versucht, solange ein Durchlauf Fortschritte macht. Dies erhält das Verhalten dynamischer Eingaben bei: Eine erfolgreiche Verbindung kann den Slot erstellen, den eine später ausstehende Verbindung benötigt. Bereits aufgelöste Verbindungen werden nicht wiederholt, und eine von einer Erweiterung abgelehnte Verbindung wird nicht erneut versucht, sobald ihre Endpunkte verfügbar sind.

Dies betrifft nur den Import von API-Prompts. Das reguläre Laden von Workflows verwendet weiterhin `graph.configure()` wie oben beschrieben, und die Signaturen der Verbindungs-Callbacks sind unverändert.

## Verbindungen ablehnen, bevor sie hergestellt werden

Um eine Verbindung abzulehnen, geben Sie `false` von `onConnectOutput` am Quell-Node oder von `onConnectInput` am Ziel-Node zurück. Beide werden ausgeführt, bevor der Graph irgendetwas ändert, sodass eine bestehende Verbindung am Eingang des Ziel-Nodes erhalten bleibt:

```js
nodeType.prototype.onConnectOutput = function (
  slot,
  type,
  input,
  targetNode,
  targetSlot
) {
  return !shouldReject(type, targetNode)
}
```

Lehnen Sie nicht über `onConnectionsChange` ab. Wenn es ausgeführt wird, hat die neue Verbindung bereits jede Verbindung ersetzt, die der Eingang des Ziel-Nodes hatte. Das Entfernen der neuen Verbindung hinterlässt den Eingang daher nicht verbunden.

## Entfernen einer Verbindung im Ausgabe-Callback überspringt den Eingabe-Callback

Beim Herstellen einer Verbindung wird zuerst `onConnectionsChange` der Ausgabeseite aufgerufen und danach das der Eingabeseite. Wenn der Handler der Ausgabeseite genau diese Verbindung entfernt, bevor er zurückkehrt, erhält die Eingabeseite durch das Entfernen einen `isConnected === false`-Callback, und ihr `isConnected === true`-Callback für die neue Verbindung wird übersprungen. Gehen Sie nicht davon aus, dass beide Seiten die Verbindung immer sehen; prüfen Sie, ob die Ihnen übergebene Verbindung noch verbunden ist, wenn Ihr Handler erneut in den Graphen eintritt. Dies ist beobachtetes Verhalten und kein getesteter Vertrag: Derzeit deckt kein Test den Pfad ab, auf dem übersprungen wird.

## Entfernte Slot-Ereignisse ersetzen

`node:slot-links:changed` und `node:slot-errors:changed` wurden entfernt; ein Ersatzereignis mit demselben Namen gibt es nicht. Migrieren Sie zu:

- `node.isInputConnected()`, `node.isOutputConnected()` oder `node.getOutputNodes()` für einen reaktiven Lesezugriff auf den Verbindungsstatus, oder
- `onConnectionsChange`, wenn Sie Code genau in dem Moment ausführen müssen, in dem ein Slot verbunden oder getrennt wird.

## Verbindungsstatus aus Callback-Argumenten oder Node-Methoden lesen

`input.link` und `output.links` sind veraltet, und Lesezugriffe können vom aktuellen Graphen abweichen. Schreibzugriffe entfernen nur Verbindungen: Wenn Sie `null` an `input.link` zuweisen, wird die Eingabe getrennt, und wenn Sie `output.links` zuweisen oder verändern, wird jede Verbindung getrennt, die im neuen Array fehlt. Schreibzugriffe erstellen niemals Verbindungen; verwenden Sie `node.connect()`, `node.disconnectInput()` oder `node.disconnectOutput()`. Verwenden Sie das Argument `link_info`, das Ihr Callback bereits erhält, oder die Instanzmethoden von `LGraphNode`, die den Verbindungsspeicher direkt lesen: `node.isInputConnected()`, `node.getInputLink()`, `node.isOutputConnected()` und `node.getOutputNodes()`. Lesen Sie `input.link` oder `output.links` nicht.

Die Speicherfunktionen hinter diesen Methoden sind intern und nicht Teil der Erweiterungs-API. Verwenden Sie die Node-Methoden.
