A deployment runs your Build on Comfy Cloud GPUs, with its own URL that the Cloud editor and your application can send Workflows to. A deployment costs GPU time while its workers run and storage until you delete it, so you keep managing it after you create it. This page shows how to release versions of the Build, choose the deployment's GPU and workers, call it, watch it, and stop or delete it.

To create your first Build and deployment, see [Custom Builds](/development/deploy/cloud-custom-builds).

<Note>
  If Comfy Cloud already supports every Node in your Workflow, you can run the Workflow on Comfy Cloud without a Build or deployment. See the [Comfy Cloud Quickstart](/development/deploy/cloud).
</Note>

## Before you begin

Each task on this page works in two places: on the Developer Platform at [platform.comfy.org](https://platform.comfy.org) in your browser, and with comfy-cli in a terminal. Make sure you have these:

- **A Build with at least one deployment**
- **For the comfy-cli tabs, comfy-cli signed in to your Comfy account**: run `comfy cloud login`.

<Tip>
  To create a Build and deployment with comfy-cli instead of the browser, run these commands in your ComfyUI folder:

  ```bash
  comfy build init
  comfy build push --release --target linux/nvidia
  comfy deploy up
  ```

  `comfy build init` writes the Build file, `comfy-build.yaml`, to the folder. Later `comfy build` commands read it, so run them in the same folder.
</Tip>

## Find your deployment

Every later task starts from the deployment, so find it first. Reading a deployment costs nothing. Pick the tab for the place you work in.

<Tabs>
  <Tab title="Developer Platform">
    1. In the **Developer Platform sidebar**, click **Deploy**.
    2. In the **Deployments** section, click the deployment's name.

    The deployment's page opens. Under its name, it shows the status, such as **Ready** or **Stopped**, and the version it runs, such as `v2`. The **Overview** tab shows its **Runtime configuration**.
  </Tab>
  <Tab title="comfy-cli">
    List every deployment in your workspace:

    ```bash
    comfy deploy ls --workspace
    ```

    Each line shows a deployment's name, its ID, its status, and the version it runs. Later commands select a deployment with `--deployment` followed by its name or ID.
  </Tab>
</Tabs>

## Release a version of your Build

A published version of a Build never changes. To add a Custom Node or a model, you publish a version, and then move the deployment onto it. The Developer Platform calls a version `v1`, `v2`, and so on. comfy-cli calls it a release.

<Tabs>
  <Tab title="Developer Platform">
    To publish a version:

    1. In the **Developer Platform sidebar**, click **Deploy**.
    2. In the **Builds** section, click your Build.
    3. Click **New version**, and make your changes in the steps.
    4. On the last step, click **Save changes**. The Build's page shows **Changed since v**_N_, where _N_ is the latest version.
    5. Click **Publish**. In the **Choose build targets** dialog, keep **Serverless build** selected, and then click **Publish**.

    Building usually takes 10 to 15 minutes. If the build fails, see [Fix a failing build or deployment](#fix-a-failing-build-or-deployment).

    To move the deployment onto the version:

    1. Open the deployment's page. When a newer version is ready, the page shows **v**_N_ **available** under the deployment's name.
    2. Click **Change version**.
    3. Select the version, and then click **Update to v**_N_.

    The deployment keeps serving the version it runs until the new one is ready, and its URL stays the same. While both run, the dialog shows the GPU time the switch costs. The update worked when the version under the deployment's name reads **v**_N_.

    To go back to an earlier version, click the **History** tab, and then click **Roll back to this version** on its row.
  </Tab>
  <Tab title="comfy-cli">
    Run these commands in the Build's folder.

    1. After you change the ComfyUI install, rescan it into the Build file:

       ```bash
       comfy build update --yes
       ```

    2. Compare the Build file with the install and with the Build on Comfy Cloud:

       ```bash
       comfy build status
       ```

    3. Push the Build file and cut a release for the `linux/nvidia` target, the target a deployment runs:

       ```bash
       comfy build push --release --target linux/nvidia
       ```

    4. Follow the release's build log until the build finishes:

       ```bash
       comfy build release logs --target linux/nvidia --follow
       ```

    5. Move the deployment onto the newest release:

       ```bash
       comfy deploy up --deployment <deployment>
       ```

    `comfy deploy up` follows the deployment until the move lands. The deployment keeps serving its current release until then, and its ID and URL stay the same.

    To go back to the release before the current one, run `comfy deploy rollback --deployment <deployment>`. To pick a release, add `--to`, such as `--to v5`.
  </Tab>
</Tabs>

<Note>
  Every version of every Build counts toward your workspace's limit of Build versions. When you reach it, delete a version you no longer need. See [Clean up](#clean-up).
</Note>

## Change the GPU or region

The GPU decides how much VRAM a Workflow gets and what each worker costs per hour. The region decides where the deployment runs, and the GPUs you can pick depend on it.

<Tabs>
  <Tab title="Developer Platform">
    You choose the **Location** when you create a deployment: **Anywhere** or **United States**. The Developer Platform can't change the location of an existing deployment. To run in another location, deploy the Build again from its page.

    To change the GPU:

    1. On the deployment's page, click **Edit settings**.
    2. In **Edit deployment**, select a GPU. Each GPU shows its VRAM and its price per hour.
    3. Click **Save changes**.
  </Tab>
  <Tab title="comfy-cli">
    1. List the regions and the GPUs each one offers:

       ```bash
       comfy deploy refs compute
       ```

       The table shows each region, each GPU class, its VRAM, and its availability. To list one region, add `--region <region>`.

    2. Set the GPU class, the region, or both:

       ```bash
       comfy deploy scale --deployment <deployment> --gpu <gpu-class> --region <region>
       ```
  </Tab>
</Tabs>

On a running deployment, a GPU or region change starts a copy of the deployment on the new GPU, and moves the deployment to it once the copy is ready. The URL stays the same, and the old copy keeps serving until then. On a stopped deployment, the change applies the next time you start it.

## Scale the workers

Each worker is one GPU that runs your jobs. Always-warm workers stay running so jobs don't wait for a GPU to start, and they cost GPU time the whole time. Max workers is the most workers the deployment runs at once when jobs arrive. With `0` always-warm workers, the deployment turns its GPUs off when no jobs come in.

<Tabs>
  <Tab title="Developer Platform">
    1. On the deployment's page, click **Edit settings**.
    2. Set **Always-warm workers** and **Max workers**.
    3. Click **Save changes**.

    The **Runtime configuration** shows the values you saved.
  </Tab>
  <Tab title="comfy-cli">
    Set both bounds together. `--min` takes `0` to `20`, and `--max` takes `1` to `20`:

    ```bash
    comfy deploy scale --deployment <deployment> --min 0 --max 3
    ```

    The command prints `Scaled deployment <id> to min=0, max=3`.
  </Tab>
</Tabs>

Your plan sets the most workers one deployment can run. To see it, open [Limits](https://platform.comfy.org/settings/limits) on the Developer Platform and check **Max workers per deployment**.

## Stop and start a deployment

Stop a deployment to keep it, with its URL and models, without running jobs. Start it again when you need it.

<Warning>
  A stopped deployment still costs storage. To stop paying for it, delete it. See [Clean up](#clean-up). Jobs still waiting to run when you stop a deployment may be dropped.
</Warning>

<Tabs>
  <Tab title="Developer Platform">
    To stop and start the deployment in the browser, see [Stop or delete your deployment](/development/deploy/cloud-custom-builds#stop-or-delete-your-deployment).

    To start a stopped deployment on another version:

    1. Click the arrow next to **Start**, and then select **Start on v**_N_.
    2. In the dialog, click **Start on v**_N_.
  </Tab>
  <Tab title="comfy-cli">
    ```bash
    comfy deploy stop --deployment <deployment>
    comfy deploy start --deployment <deployment>
    ```

    Each command prints that the service accepted it. To follow the deployment until it settles, run `comfy deploy status --deployment <deployment> --watch` in the Build's folder.
  </Tab>
</Tabs>

## Call your deployment from your application

Your application sends API-format Workflows to the deployment's URL with the [Comfy API v2](/api-reference/v2/overview), using a workspace API key. Before you send a job, check that the deployment's status reads **Ready**. A job on a deployment with `0` always-warm workers can wait a few minutes while a GPU starts.

<Tabs>
  <Tab title="Developer Platform">
    1. On the deployment's page, find **Run via API** on the **Overview** tab.
    2. Copy the **Deployment URL**.
    3. Click **Create API key**, and copy the key.
    4. Copy the Python, JavaScript, or cURL snippet, and run it with the key in the `COMFY_API_KEY` environment variable.

    To try the deployment from the page first, use **Test this deployment**. **Quick test** runs a small Workflow with no models and uses GPU time. Click **Run**. The test worked when it reads **Finished in** followed by the time it took.
  </Tab>
  <Tab title="comfy-cli">
    Send an API-format Workflow and wait for its outputs:

    ```bash
    comfy deploy run --deployment <deployment> --workflow workflow_api.json
    ```

    The command waits for the job and downloads its outputs to the `outputs` folder. To save them elsewhere, add `--output-dir <folder>`.
  </Tab>
</Tabs>

From your own code, use the [Comfy SDKs](/development/api-development/sdks). Set `COMFY_BASE_URL` to the Deployment URL. See [Choosing a base URL](/development/api-development/sdks#choosing-a-base-url).

## Use workspace library models in API requests

A deployment runs `.safetensors` models from your workspace library, even when its release doesn't include them. To pick a LoRA per request, upload it to the library once, and then name it in each Workflow you send. To upload a model in the Comfy Cloud editor or on the Developer Platform, and for the plan and file size it needs, see [Add your own LoRA or model](/development/deploy/cloud-custom-builds#add-your-own-lora-or-model).

To upload from a terminal, set the model type with `--type`:

```bash
comfy assets library upload my_style.safetensors --type loras
```

The upload worked when the command prints `Added my_style.safetensors to loras`.

In the [API-format Workflow](/development/api-development/workflow-api-format), set the loader input to the library file name, including `.safetensors`:

```json
"10": {
  "class_type": "LoraLoader",
  "inputs": {
    "lora_name": "my_style.safetensors",
    "strength_model": 1.0,
    "strength_clip": 1.0,
    "model": ["4", 0],
    "clip": ["4", 1]
  }
}
```

Send the Workflow with `comfy deploy run`, the [Comfy SDKs](/development/api-development/sdks), or the [Comfy API v2](/api-reference/v2/overview):

```bash
comfy deploy run --deployment <deployment-id> --workflow workflow_api.json
```

To use a different LoRA, change `lora_name` to another library file name in the next request. You don't need a new Build, release, or redeploy.

- A Workflow can name up to 100 library models. A loader that names a 101st library model fails as if the file were not in the library.
- Keep file names unique across the folders one loader reads. If the library has the same file name in two of them, a job sent through the API loads neither file.

## Monitor a deployment

Check a deployment's state when it starts, after you change it, and when jobs fail.

<Tabs>
  <Tab title="Developer Platform">
    On the deployment's page:

    - The status under the deployment's name reads **Queued**, **Provisioning**, or **Starting** while the deployment comes up, and **Ready** when it serves jobs.
    - While the deployment comes up, **Deployment progress** shows each step, such as **Copying models**. It runs on Comfy's side, so you can close the page and come back.
    - The **Boot log** tab shows what ComfyUI printed while the deployment started.
    - The **History** tab lists the versions the deployment ran and what moved it.

    On the **Deploy** page, the **Deployments** section shows each deployment's GPU credits over the last seven days in **Spend · 7d**. Model storage isn't included.
  </Tab>
  <Tab title="comfy-cli">
    In the Build's folder, follow the deployment until it settles:

    ```bash
    comfy deploy status --deployment <deployment> --watch
    ```

    The command reports the status, such as `Deployment <name>: ready`, whether a newer release is waiting, and how many jobs are queued. To read more:

    ```bash
    comfy deploy logs --deployment <deployment>      # what ComfyUI printed while it started
    comfy deploy events --deployment <deployment>    # its status changes, in order
    comfy deploy history --deployment <deployment>   # the releases it ran
    ```
  </Tab>
</Tabs>

## Clean up

Delete what you no longer use. Deleting a deployment stops its storage cost. Deleting a version frees a place in your workspace's limit of Build versions. You can't delete a Build or a version while a deployment uses it, so delete the deployment first.

<Warning>
  Deleting a deployment, a version, or a Build is permanent. Deleting a deployment keeps the Build and its versions, so you can deploy again later.
</Warning>

<Tabs>
  <Tab title="Developer Platform">
    To delete a deployment, see [Stop or delete your deployment](/development/deploy/cloud-custom-builds#stop-or-delete-your-deployment).

    To delete a version, open the Build's page. On the version's row, open **Version actions**, select **Delete version**, and then click **Delete**.

    To delete the Build, click **Delete** on the Build's page, and then click **Delete** in the **Delete build** dialog.
  </Tab>
  <Tab title="comfy-cli">
    ```bash
    comfy deploy delete --deployment <deployment>
    comfy build release delete <release-id>
    comfy build delete --id <build-id>
    ```

    Each command asks you to confirm. To list a Build's releases and their IDs, run `comfy build release ls --id <build-id>`. To list your Builds, run `comfy build ls`.
  </Tab>
</Tabs>

## Fix a failing build or deployment

When a build or a deployment fails, its logs name the cause. Fix the cause, and then publish or start again.

<AccordionGroup>
  <Accordion title="The build failed">
    On the Developer Platform, follow [What if the build fails?](/development/deploy/cloud-custom-builds#publish-the-build) in Custom Builds.

    With comfy-cli, read the release's state and its build log in the Build's folder:

    ```bash
    comfy build release show
    comfy build release logs --target linux/nvidia
    ```

    Change the ComfyUI install, such as by removing the Custom Node that failed, and then [release again](#release-a-version-of-your-build).
  </Accordion>

  <Accordion title="The deployment status reads Failed">
    The deployment's page shows the error with _This deployment didn't start. Fix what the error names, then start it again._ Click **Copy** to copy the error. The **Boot log** tab shows what ComfyUI printed.

    With comfy-cli, `comfy deploy status` prints the reason, and `comfy deploy logs` and `comfy deploy events` show the log and the status changes.

    Fix what the error names, and then start the deployment again.
  </Accordion>

  <Accordion title="The deployment takes a long time to start">
    Follow the steps in **Deployment progress** on the deployment's page, or run `comfy deploy status --deployment <deployment> --watch`. The **Copying models** step takes longer the more models the version has. When you create a deployment on the Developer Platform, **Estimated time** in the deploy dialog shows how long it should take.

    If the GPU you picked has no capacity, [change the GPU or region](#change-the-gpu-or-region). With comfy-cli, `comfy deploy refs compute` shows each GPU's availability.
  </Accordion>

  <Accordion title="The status reads Stopped: out of credits">
    The deployment stopped because your workspace ran out of credits. Add credits, and then start the deployment again.
  </Accordion>

  <Accordion title="The status reads Stop failed">
    The deployment couldn't stop and may still be billing. Click **Stop** again, or run `comfy deploy stop --deployment <deployment>` again.
  </Accordion>

  <Accordion title="An update to a version failed">
    The deployment page reads **Update to v**_N_ **failed.**, and the deployment keeps serving the version it ran before. Click **Retry**, or fix the version and release again.
  </Accordion>
</AccordionGroup>

## FAQ

<AccordionGroup>
  <Accordion title="Can one Build come from multiple Workflows?">
    Yes. When you create a Build on the Developer Platform, you can upload one or more Workflows to preselect their models and Custom Nodes. Include the dependencies of all the Workflows you plan to run, and then send each API-format Workflow to the deployment.

    Each deployment uses one GPU. To run Workflows on different GPUs, create separate deployments of the same Build.
  </Accordion>

  <Accordion title="Am I charged for storing Builds that are not deployed?">
    No. Builds and their versions are stored at no charge. Storage billing starts when you deploy:

    - When you deploy a version, its models are copied onto network storage that the deployment's workers share. The storage is billed per GB per month for as long as a deployment of the Build exists in that region, including while the deployment is stopped. Models a job uses from your [workspace library](/development/deploy/cloud-custom-builds#add-your-own-lora-or-model) aren't copied there. The worker downloads them for the job.
    - Each worker also has its own local disk. It isn't billed separately. The GPU rate covers it.
    - Deleting a deployment releases its compute. Billing for the network storage ends when you delete the last deployment that uses it.

    For storage and GPU rates, open [Limits](https://platform.comfy.org/settings/limits) on the Developer Platform and check **Deployment pricing**. The deploy dialog's **Estimated cost** panel also shows the GPU time and model storage for a deployment.
  </Accordion>

  <Accordion title="How are always-warm workers billed?">
    **Always-warm workers** (`--min` in comfy-cli) stay running at all times, so jobs never wait for a GPU to start. They bill GPU time for as long as they run, whether or not they process jobs.

    Workers above that number, up to **Max workers** (`--max`), start when jobs arrive. They bill GPU time from the moment they start, through their jobs, and for the idle time after their last job before they're released. By default, a worker stays up for 3 minutes after its last job. You can set that time, from 30 seconds to 20 minutes, in **Keep worker up after a job** when you create the deployment on the Developer Platform. With `0` always-warm workers, the deployment bills no GPU time while it's idle, and the first job waits while a GPU starts.

    If your workspace runs out of credits, its deployments stop.

    For GPU rates, open [Limits](https://platform.comfy.org/settings/limits) on the Developer Platform and check **Deployment pricing**. Rates are per worker, for each hour it runs.
  </Accordion>

  <Accordion title="How does a deployment handle multiple requests?">
    A deployment spreads requests across its workers and adds workers, up to **Max workers**, as jobs arrive. Requests that can't run at once wait in the deployment's queue until a worker is free.
  </Accordion>

  <Accordion title="What happens when I delete a deployment?">
    Deleting a deployment removes its URL and releases its compute. It doesn't delete the Build or its versions. After you delete the last deployment that uses the Build's network storage in a region, storage billing for it ends.

    Deleting the Build is a separate step. See [Clean up](#clean-up).
  </Accordion>
</AccordionGroup>
