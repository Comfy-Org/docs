モデル ID でアドレス指定される Comfy Router の正規ルート。

ベース URL: `https://api.comfy.org`

以下のすべてのエンドポイントは認証が必要です。`X-API-Key: <api-key>` または `Authorization: Bearer <jwt>` を送信してください。

Comfy API キーは Bearer トークンとして送信することもできます。両方の認証ヘッダーが指定された場合、`X-API-Key` が優先されます。キーと JWT の違いについては[認証ヘッダー](/ja/development/comfy-router/headers#リクエストヘッダー)を、アクセス要件については[クイックスタート](/ja/development/comfy-router/quickstart)を参照してください。

### `POST /v2/models/{provider}/{model}`

**正規のモデル ID を指定してパートナーモデルを同期的に実行します。**

モデルを実行し、完了した結果を同じレスポンスで受け取ります。

**パラメータ**

<ParamField path="provider" type="RouterProviderSegment" required>
  正規の `{provider}/{model}` モデル ID のプロバイダー部分。

  型: [`RouterProviderSegment`](#routerprovidersegment) -- 英数字スラッグ（例: `anthropic`）、最大 64 文字
</ParamField>

<ParamField path="model" type="RouterModelSegment" required>
  正規の `{provider}/{model}` モデル ID のモデル部分。

  型: [`RouterModelSegment`](#routermodelsegment) -- 英数字スラッグ（例: `claude-opus-4-6`）、最大 128 文字
</ParamField>

<ParamField header="Idempotency-Key" type="string">
  呼び出し元が生成するキーで、1 つの論理的な呼び出しの再試行を安全にします。

  1〜255 文字
</ParamField>

<ParamField query="model_provider" type="string">
  このモデルを現在のデフォルトの代わりに処理する代替プロバイダーを選択します。`fal`、`wavespeed`、`runware`、`higgsfield` が代替プロバイダーであり、`GET /v2/models/{provider}/{model}` は、あるモデルがそのうちどれをサポートしているかを報告します。拒否は固定された順序でチェックされ、前段のチェックは後段のチェックの結果に関係なく応答します。未認識の値、つまり登録済みプロバイダーでないものは `400` で拒否されます。次に、ボディがマルチパート操作（編集）を選択するリクエストで代替プロバイダーを指定した場合、`detail` が「this request's `image` selects the edit operation」で始まる `409` で拒否されます。ただし、そのプロバイダーのこのモデル用トランスレーターがその操作を処理できない場合に限ります。メディアを扱えるトランスレーターを持つレッグは通常どおり処理されます。次に、bring-your-own-key 認証情報が解決されたリクエストでは、そのプロバイダーがこのモデルを処理するかどうかに関係なく、代替プロバイダーは `detail` が `this request resolved a BYOK credential` で始まる `409` で拒否されます（そのレスポンスを参照）。次に、指定されたプロバイダー自身のゲートがあり、そのプロバイダーがあなたに対して有効化されていない場合は `error_type: not_enabled` を伴う `403` で、ゲートを評価できない場合は `error_type: service_unavailable` を伴う `503` で拒否します。そして、これら 4 つすべてを通過した後にのみ、このモデル用のレッグを持たない実在のプロバイダーが `error_type: invalid_input` を伴う `400` で拒否されます。これは未認識の値と同じ応答です。`fallback_provider` は、bring-your-own-key リクエスト、ボディがマルチパート操作を選択するリクエスト、および `strict_mode=true` の場合には、拒否されるのではなく無効になります。
</ParamField>

<ParamField query="strict_mode" type="boolean">
  `model_provider` と組み合わせた場合にのみ意味を持ちます。

  デフォルト: False
</ParamField>

<ParamField query="fallback_provider" type="string">
  最初の試行が Router または試行したプロバイダーに起因する理由で失敗した場合に、Router がこの呼び出しをモデルの他の登録済みプロバイダーに対して再試行するかどうかを制御します。省略した場合、または `false` 以外の値の場合はフォールバックが有効のままです。`false` で無効になります。フォールバックが成功したレスポンスには `X-Comfy-Router-Fallback-Provider` が付与されます。bring-your-own-key 認証情報が解決されたリクエストでは、このパラメータの値に関係なくフォールバックは利用できません。試行は単に行われず、最初の失敗がそのまま返されます。これは拒否ではなく無効であり、ここから `409` が発生することはありません。同じ理由で、ボディがマルチパート操作を選択するリクエストおよび `strict_mode=true` の場合も同様です。いずれも呼び出しを 1 つのプロバイダーに結び付け、別のプロバイダーに対して忠実に再生することはできないため、フォールバックは拒否されるのではなく単にスキップされます。その `409` で拒否されるのは明示的な `model_provider` のみであり、この無条件のスキップとは異なり、マルチパートの `409` はトランスレーターがその操作を処理できないレッグにのみ適用されます。
</ParamField>

<ParamField query="reject_unknown_fields" type="boolean">
  このモデルの入力スキーマが宣言していないトップレベルのリクエストボディフィールドを、受け入れるのではなく拒否することをオプトインします。ネストされたフィールドはチェックされません。スキーマが未宣言のフィールドを許可しているモデル、または作成済みのスキーマを持たないモデルでは何も拒否されず、`strict_mode=true` で送信されたキュー中の送信でも同様です。

  デフォルト: False
</ParamField>

**リクエストボディ**

`application/json` -- [`RouterModelInput`](#routermodelinput)（必須）

パートナーモデルのネイティブ JSON 入力です。`model_provider` を指定しない場合、リクエストはモデルのデフォルトプロバイダー上でネイティブディスパッチを実行し、このボディはモデル自身のネイティブスキーマとなって、そのまま転送されます（`strict_mode` はそこでは意味を持たず、何も変わりません）。`model_provider` が代替プロバイダーを選択し、`strict_mode=false`（デフォルト）の場合、ボディは送信前にそのプロバイダーの実際のスキーマへ変換されます。正確に表現できないネイティブフィールドはドロップされ、レスポンスの `X-Comfy-Router-Dropped-Params` ヘッダーで開示されます。暗黙に破棄されることはありません。`model_provider` が代替プロバイダーを選択し、`strict_mode=true` の場合、変換は実行されません。ボディはすでにその代替プロバイダー自身の実際のスキーマである必要があり（このモデルのネイティブなものではありません。`strict_mode` を参照）、そのまま転送されます。ボディのフィールド自体も、複数の操作をサポートするモデルで Router が実行する操作を選択します。編集可能な画像モデルの場合、入力画像を含めるとテキストから画像への操作から画像から画像へ（編集）の操作に切り替わり、これには独自のレートが適用される場合があります。Seedance ビデオモデルの場合、`content[].role` が操作を選択します（最初のフレーム画像は画像から動画へを選択し、参照画像またはクリップは参照から動画を選択します）。ネイティブディスパッチでは、Seedance の課金は役割ではなく `content` 内のメディア種別に従います。動画入力が含まれるリクエストは動画から動画へとして課金され、そうでなければ画像が含まれるものは画像から動画へとして、それ以外はテキストから動画へとして課金されます。ただし、`draft_task` アイテムからの最終レンダーは、それがレンダリングする Draft の操作として課金されます。一部のモデルではテキストから動画へと画像から動画へが同じレートで課金されます。`model_provider` が代替プロバイダーを選択する場合、条件付けされた各操作にはそのプロバイダー独自のレートが適用される場合があります。

### `POST /v2/models/{provider}/{model}/estimate`

**モデル呼び出しを実行する前に、実行せずに価格を見積もります。**

このボディをこのモデルで実行した場合のコストを米ドルで事前に見積もって返します。価格は Comfy の標準定価に基づきます（ベンダーが報告するコストで請求されるモデルは、代わりにベンダーの公開価格表から見積もられます）。契約料金や顧客固有の料金は反映されません。交渉済みの価格を持つワークスペースには定価が提示され、契約料金が請求されます。その場合、`source: exact` は定価に対して正確であることを意味し、そのワークスペースの請求額を意味するわけではありません。これは見積もりであり、最終請求額ではありません。実際に支払うのは、ワークスペースの使用量と請求の記録に確定した請求額です。ボディはまずモデルの入力スキーマに対して検証されます。これはデフォルトの実行（`strict_mode` なし、`reject_unknown_fields` なし）が検証するのと同じです。そのため、モデルのスキーマ検証に失敗するボディは、ここでも実行時と同じ `422` になります。プロバイダーには何もディスパッチされず、何も請求されません。この応答は価格を固定するものではありません。`pricing_as_of` 時点で有効な料金で価格設定され、実行は、レート適用時点で有効な料金で請求されます。デプロイメントで見積もりが無効になっている場合、このルートは `403` を `error_type: not_enabled` とともに返します。Router がまだ実行できないモデルは、実行ルート独自の `detail` を伴う同じ `403` を返すため、両者を区別するには `detail` を読んでください。ボディは Router がディスパッチするのと同じ方法で価格設定されます。ボディが指定する `model_provider` レッグ向けに変換され、実行されるオペレーションに再ターゲットされます。順序は、キュー中の送信の `201` にある `estimate` と同じです。ただし、その `estimate` は事前価格ではありません。実行が受け入れられてキューに入った後にのみ到着し、その実行は、ディスパッチ前にキャンセルされない限り請求されます。

### `POST /v2/models/{provider}/{model}/requests`

**パートナーモデルの実行をキューに送信し、すぐに戻ります。**

Comfy Router のキュー配信モードです。リクエストボディは、`POST /v2/models/{provider}/{model}` がこのモデルに対して受け付けるものと同じパートナーネイティブの JSON 入力です（1つのボディ形状、モデルごとに1つのスキーマ、2つの配信モード）。ただし、このルートは結果のために接続を保持しません。実行を受け付け、ハンドルとともに `201` を返し、呼び出し元は後で以下の3つの読み取りによって結果を取得します。

**リクエストボディ**

`application/json`: [`RouterModelInput`](#routermodelinput)（必須）

パートナーモデルのネイティブ JSON 入力で、同期ルートがこのモデルに対して受け付けるボディと同じものです。また、操作を選択し、同じ方法で課金されます。ボディ自身のフィールドが、複数の操作をサポートするモデルで Router が実行する操作を選択します（入力画像は編集可能な画像モデルを画像から画像へ切り替え、それには独自のレートで課金される場合があります。Seedance の最初のフレーム画像は画像から動画へを選択し、参照画像またはクリップは参照から動画を選択します）。ネイティブディスパッチでは、Seedance リクエストはロールではなく `content` 内のメディア種別で課金されます。ビデオ入力があれば動画から動画へとして課金され、そうでなければ画像があれば画像から動画へ、それもなければテキストから動画へとして課金されます。ただし、`draft_task` 項目からの最終レンダーは、それがレンダリングする Draft の操作として課金されます。一部のモデルではテキストから動画へと画像から動画へに同じレートを請求します。`model_provider` で代替プロバイダーを選択する場合、条件付けされた各操作はそのプロバイダー独自のレートで課金される場合があります。同じプロバイダー選択の契約がディスパッチ時に適用されます。`model_provider` を指定しない場合、または `model_provider` を指定して `strict_mode=false`（デフォルト）の場合、ボディはモデルのネイティブドキュメントであり、実行が受け付けられる前にモデル自身の入力スキーマに対して検証されます。そのため、モデルが拒否するようなボディは、数分後に失敗するキュー中のリクエストではなく、ここで `422` になります。非厳格な代替プロバイダーのボディは、さらにディスパッチ時にそのプロバイダーの実際のスキーマへ変換されます。`strict_mode=true` の場合、ボディはすでに代替プロバイダー自身のスキーマである必要があり、変更されずに転送されます。ネイティブスキーマの検証は、同期ルートとまったく同じようにスキップされます（`model_provider` と `strict_mode` を参照）。

## エラーバケット

Router の機械可読なエラーカテゴリで、`X-Comfy-Error-Type` ヘッダーでも送信されます。

### リクエストレベルバケット

Router が受け付けたものの、完了できなかったリクエストに対して発生します。

| `error_type` | 意味 |
| --- | --- |
| `invalid_input` | リクエストがモデルに到達する前に拒否されました。ボディの形式が不正、ページネーションカーソルが不正または期限切れ、モデル自身のスキーマが受け付けない入力、またはこのリクエストに使用できない `Idempotency-Key`（別のリクエストで既に使用済み。方法、パスとクエリ、またはボディが異なる。もしくは、レスポンスを再生できない呼び出しによって既に消費済み）です。 |
| `content_policy_violation` | プロバイダーがコンテンツポリシーを理由にリクエストを拒否しました。 |
| `provider_error` | パートナープロバイダーが自身の障害を報告したか、Router が結果として解釈できないレスポンスを返しました。 |
| `provider_timeout` | パートナープロバイダーが期限までに応答しませんでした。 |
| `insufficient_credits` | 呼び出し元のワークスペースに、モデルを実行するための十分なクレジットがありません。 |
| `model_not_found` | `{provider}/{model}` という ID が、Router で実行できるモデルを指していません。不明なプロバイダー、未登録の ID、カタログが提供終了日を過ぎて廃止したモデル、またはプロバイダーが現在 Comfy 向けに提供していないカタログ登録済みの ID です。 |

### トランスポートレベルバケット

モデルへの呼び出しの前またはその周辺で、Router 自身によって発生します。

| `error_type` | 意味 |
| --- | --- |
| `unauthorized` | リクエストに利用可能な認証情報が含まれていませんでした。 |
| `forbidden` | 認証情報は有効ですが、このモデルまたはこの操作に対する権限がありません。 |
| `concurrency_limit_exceeded` | ワークスペースはすでに許可された数の呼び出しを実行中です。いずれかが完了したら再試行してください。 |
| `client_disconnected` | 呼び出し側が、Router が結果を返す前に接続を閉じました。 |
| `internal_error` | Router 自体が失敗しました。 |
| `deadline_exceeded` | 回答が到着する前に、Comfy が自身の設定済みの上限で接続の維持を停止しました。 |
| `not_enabled` | この呼び出し側に対して Comfy Router がまだ有効になっていません。 |
| `service_unavailable` | Comfy Router が依存するサービスが一時的に利用できず、呼び出し側に問題はありません。 |
| `rate_limited` | 呼び出し側がウィンドウ単位で測定される割り当てを消費し、そのウィンドウが経過するのを待つ必要があります。 |
| `cancelled` | キューに入っていたリクエストが、結果を生成する前に、キャンセルルートまたはオペレーターによって取り消されました。これは終端状態であり、それ自体は課金に関する表明ではありません。 |
| `queue_timeout` | キュー中のリクエストが、一度も受け入れられることなくキュータイムアウトを超えて待機し続けました。 |
| `request_not_found` | `request_id` が、このモデルにおける呼び出し元のどのリクエストも指していません。 |
| `queue_backlog_full` | 呼び出し元が既に実行待ちのキュー中リクエストを抱えすぎているため、この送信は拒否されました。 |
| `result_expired` | リクエストは存在し、完了していましたが、その結果はもう保存されていないため、collect に返すものがありません。 |

<ResponseField name="X-Comfy-Estimated-Duration-P90-Seconds" type="integer">

<ResponseField name="X-Comfy-Estimated-Duration-Seconds" type="integer">

<ResponseField name="X-Comfy-Refusal-Subject" type="string">

</ResponseField>

<ResponseField name="X-Comfy-Request-Id" type="string">

</ResponseField>

</ResponseField>

## 事前のコスト見積もり

`POST /v2/models/{provider}/{model}/estimate` は、実行せずにボディの料金を見積もります。また、キューに投入される送信（`POST /v2/models/{provider}/{model}/requests`）は、その `201` で `estimate` と同じ [`RouterCostEstimate`](#routercostestimate) を返します。どちらも Comfy の標準リスト価格で価格設定されます。ただし、ベンダーが報告するコストで請求されるモデルは例外で、そのコストはベンダーの公開価格表から `estimated` として算出されます。どちらも契約料金や顧客固有の料金を反映しません。交渉価格のあるワークスペースにはリスト価格が提示され、契約料金が請求されます。その場合、`source: exact` はリスト価格に対して正確という意味であり、そのワークスペースの請求額に対して正確という意味ではありません。どちらが返す数値も見積もりであり、最終請求額ではありません。ワークスペースの使用量および請求記録にある確定請求額が最終です。自分のプロバイダーキーでの実行は Comfy から請求されません（以下を参照）。デプロイで見積もりが無効になっている場合、ルートは `403` と `error_type: not_enabled` を返し、送信レスポンスは `estimate` を省略します。どちらも、Router がディスパッチする形でボディの料金を見積もります（`model_provider` レッグ用に変換され、実行されるオペレーションにリターゲットされます）が、送信時の `estimate` は実行前の価格ではありません。これは実行が受け入れられ、キューに入った後にのみ返され、その実行はディスパッチ前にキャンセルされない限り請求されます。カタログには依然として価格が掲載されていません。

金額より先に `source` を読んでください。数値の欠落は無料を意味しません。

| `source` | 含まれるもの | 読み方 |
| --- | --- | --- |
| `exact` | `amount`、`amount_cents`、`credits` | `pricing_as_of` の料率でこのボディに対して請求される額と等しい見積もりです。ワークスペースの使用量および請求記録にある確定した請求額が最終的な金額です。 |
| `estimated` | `min_amount`、`max_amount` とその `_cents` 形式、`amount` は含まれない | プロバイダーが報告する数量に請求額が依存し、その数量の上下限がボディで決まる見積もりです。請求額は上下限の範囲内になると見込まれ、ワークスペースの使用量および請求記録にある確定した請求額が最終的な金額です。 |
| `free` | `amount` は "0"、`amount_cents` と `credits` は `0` | 料率表がこのリクエストをゼロで価格付けするため、見積もりは `0` です。ワークスペースの使用量および請求記録にある確定した請求額が最終的な金額です。`0` と表示されるのは `free` の見積もりだけです。 |
| `unknown` | `reason`、数値なし | 実行前に価格を提示できませんでした。その他の `source` 値は `unknown` として扱ってください。 |

`unknown` の見積もりの `reason` は次のいずれかです:

- `not_quotable`: Router はこの呼び出しを実行前に価格付けできません。プロバイダーが報告する数量で請求され、その数量の上下限がボディで決まらないか、送信されたままのボディを価格付けできないためです。認識できない `reason` は `not_quotable` として扱ってください。
- `unpriced_model`: 料率表がこのリクエストを価格付けしていません。
- `byok`(キュー中の送信のみ): 実行は自分のプロバイダーキーを使用するため、Comfy は何も請求しません。
- `pricing_unavailable`(キュー中の送信のみ): リクエストの受け付け時に料率表を読み取れませんでした。送信はそのまま受け付けられ、実行は通常どおり請求されます。

Router がまだ実行前に価格付けできないモデルは、[事前見積もりのないモデル](/ja/development/comfy-router/limitations#事前見積もりのないモデル)に一覧されています。そこに載っていないモデルでも、特定のボディでは `unknown` を返すことがあるため、すべての見積もりで `source` を読んでください。

見積もりがフェイルクローズするのは次の場合です:

- 数値に料率表が必要で、カードが読み込まれていないか古い場合、`/estimate` は推測ではなく `503` を返します。キュー中の送信は見積もりを理由に拒否されることはなく、代わりに `source: unknown` と `reason: pricing_unavailable` を含みます。実行前にまったく価格付けできない呼び出し(`not_quotable`)、または自分のプロバイダーキーでのキュー中の送信(`byok`)は、カードを読まずに応答されるため、その `200` はカードが新しいかどうかについては何も示しません。
- `/estimate` はデフォルトの実行と同様に、モデル自身の入力スキーマに対してボディを検証します。そのため、モデルのスキーマに適合しないボディは、実行が返すのと同じ `422` を、同じ `detail[]` 形状で受け取ります。何も価格付けもディスパッチもされません。
- キュー中の送信の冪等なリプレイ(`Idempotent-Replayed: true`)は `estimate` を含みません。元の見積もりが保存されていないためです。

見積もりの限界。`200` の数値は、実行が受け付けられること、または正確にその金額が請求されることを約束するものではありません:

- `/estimate` は `strict_mode` や `reject_unknown_fields` を受け取らないため、モデルのネイティブな契約のみを検証します。`strict_mode=true` の実行が代替プロバイダー自身のスキーマで受け付けるボディが、ここでは `422` になることがあります。また、`reject_unknown_fields=true` の実行なら拒否する未宣言のトップレベルフィールドが、ここでは価格付けされます。Anthropic Messages モデルは例外です。そのスキーマは未宣言のフィールドを許容するため、`reject_unknown_fields=true` の実行でも何も拒否せず、見積もりは未宣言のトップレベルフィールド `tools`、`tool_choice`、`temperature`、`top_p`、`top_k`、`stop_sequences`、`metadata`、`thinking` および空の `mcp_servers` のみを価格付けします。その他の未宣言のトップレベルフィールドがあると、`reason: not_quotable` とともに `unknown` を返します。
- `pricing_as_of` は料率表を取得した時刻です。ベンダーの公開価格表から取得した `estimated` の見積もりは、その価格表を読んだ日付を持ちます。請求数量をベンダーの公開スケジュールから予測し、その後レートカードで価格設定する `exact` または `estimated` の見積もりは、そのスケジュールの読み取り日がカードより古い場合、スケジュールの読み取り日を持ちます。カードもスケジュールも読まれていない場合は、見積もりを返した時刻です。これは価格の固定ではありません。実行は、レーティング時点で有効な料率で請求されます。
- `/estimate` は `model_provider` が示すレグ、またはネイティブのプロバイダーを価格付けします。`fallback_provider` や `strict_mode` パラメータは受け取りません。フォールバックのリトライが別のプロバイダーで行われる同期実行は、そのプロバイダーの料率で請求され、見積もりはそのレグを価格付けしていません。実行のレスポンスの `X-Comfy-Router-Fallback-Provider` が、それが発生したことを示します。キュー中の送信にはフォールバックがないため、その `estimate` は実行されるレグを価格付けします。
- `/estimate` とキュー中の送信の `estimate` は、`model_provider` レグの同じボディ、または兄弟オペレーションで実行されるボディについて、わずかに異なるドキュメントを価格付けすることがあります。送信の `estimate` は、実行が送信するドキュメントに基づいて価格付けされます。
- `/estimate` は常にプラットフォームの請求額を算出します。自分のプロバイダーキーでの実行は Comfy から請求されませんが、`/estimate` はそれを検出せずに数値を返します。`reason: byok` を返すのはキュー中の送信だけです。- ドルは丸めていないセントから最大8桁の小数で表示され、課金対象の1セント未満の `amount` が `0` と表示されることはありません。`credits` は `round(amount × 211, 2)` であり、これは `X-Comfy-Credits-Used` が課金に適用するのと同じ変換です。そのため、ごく小さい非ゼロの価格では `credits` が `0` にラウンドされることがあります。これが重要となる場合は、`credits` ではなく `amount` または `amount_cents` で予算を立ててください。このヘッダーは引き続き、1回の実行に対する事後的な数値です。残高は Comfy プラットフォーム上にあります。

## 結果アセット

モデルは、アセット URL、インラインバイト、またはその両方を返すことができます。以下のプロバイダーは、選択済みのアセットを Comfy ストレージにコピーし、その URL を置き換えます。この動作はモデルによって異なります。これを選択するリクエストヘッダーはありません。

| モデル | Comfy ストレージにコピーされるもの | Comfy ホスト URL の最大有効期間 |
| --- | --- | --- |
| `bfl/*` | 完了したアセット、および結果に含まれている場合はドラフトキャッシュのアセット | 24 時間 |
| `byteplus/*` ビデオモデル (`seedance`、`dreamina-seedance`) | 完了したビデオ、および結果に含まれている場合はラストフレーム画像 | 24 時間 |
| `minimax/*` | 完了したビデオ | 12 時間 |
| `xai/*` | 生成されたすべての画像、および完了したビデオ | 24 時間 |

これらの有効期間は、URL を開いたときではなく、URL が署名されたときに開始されます。キャッシュされた URL や再利用された URL は残り時間が短い場合があります。再利用しても有効期間は更新されません。`Idempotency-Key` の記録は、保持する URL より長く残ることがあるため、そうした URL の有効期限が切れる 1 時間前から、同じキーでの再試行は記録済みのレスポンスではなく `409 invalid_input` で応答されます。応答が返された時点ですでにそれだけ期限に近かった場合は、5 分間は再再生できます。アセットは速やかにダウンロードしてください。コピーされるのは各行に記載されたアセットのみです。`byteplus/seedream-*` と `byteplus/seededit-*` の画像は BytePlus ビデオの行には含まれません。

コピーを実行するのは、モデルのネイティブプロバイダーのみです。代替プロバイダーによって処理された実行、つまり `model_provider` が代替プロバイダーを指定している場合、またはネイティブ実行のフォールバック再試行が代替プロバイダーに到達した場合（`X-Comfy-Router-Fallback-Provider` で開示されます）は、そのプロバイダー自身の URL を返します。これらの URL はプロバイダーの有効期限に従い、コピーされません。`model_provider` の値 `default`、`comfy`、`comfyui` は代替プロバイダーを指定しないため、それらの実行はネイティブであり、上記と同様にコピーされます。フォールバック再試行がネイティブプロバイダーに戻った `model_provider` の実行も同様です。

**Veo (`veo/*`) には別のストレージパスがあります。** `response.videos[]` では、存在する方のメンバーを読み取ってください。`bytesBase64Encoded` はクリップをインラインで含み、`gcsUri` は、プロバイダーから Comfy ストレージへの直接書き込みが環境で構成されている場合に、Comfy が署名した HTTPS リンクを含みます。そのリンクはレスポンスから 24 時間有効です。後者の場合はアセットをコピーするのではなく直接書き込むため、Veo は再ホスティングの表には含まれていません。

その他のモデルは、プロバイダーのアセット参照またはインラインバイトを返します。プロバイダーの URL はプロバイダーの有効期限に従います。これは上記の有効期間よりはるかに短い場合があり、Router の契約では規定されていません。

**オリジナルの BytePlus URL（Seedance 2.x、オプトイン）。** Comfy がサーバー側でオプトインしたワークスペースでは、Seedance 2.x の結果に、コピーされた URL の隣に BytePlus 自身の URL が `content.upstream_video_url` と `content.upstream_last_frame_url` として含まれ、さらに `content.upstream_expires_at` も含まれます。リクエストパラメーターはなく、デフォルトでオプトインされるワークスペースはありません。これらの URL は生成から 24 時間後に期限切れとなり、BytePlus がクリアすると存在しなくなります。Seedance 2.5 では BytePlus がそれぞれ 100 ダウンロードに制限しており、Router 自身のコピーがそのうち 1 回を使用します。各 URL はそのオブジェクトのベアラークレデンシャルです。保持している誰でも、期限が切れるまでアセットをダウンロードできます。

**ゼロデータ保持のワークスペース。** Comfy がゼロデータ保持を設定したワークスペースでは、BytePlus の結果は Comfy ストレージにコピーされません。上記の `byteplus/*` ビデオの行は適用されず、`content.video_url` と `content.last_frame_url` は BytePlus 自身のプロバイダー URL となり、BytePlus が送信したそのままの形で返されます。これらは 24 時間有効で、Seedance 2.5 では BytePlus がそれぞれ 100 回のダウンロードに制限しているため、アセットは速やかにダウンロードしてください。このような結果は `Idempotency-Key` レコードから再生されません。

コピーはアセットごとのベストエフォートです。1 つのコピーが失敗した場合、そのエントリはプロバイダーの参照を保持します。レスポンスには Comfy とプロバイダーの両方の URL が含まれる可能性があり、アセットごとの明示的なコピーステータスフィールドはありません。生成は引き続き成功し、課金されます。1 つの正常に再ホストされたアセットから、すべての URL の有効期間を推測しないでください。

結果が Comfy ホストかどうかは、完了した呼び出しが後でその `Idempotency-Key` レコードから再生できるかどうかも決定します。上記の `Idempotency-Key` パラメーターは、再生できない場合に再試行が何で応答されるかを説明しています。

## モデルごとの入力および出力スキーマ

各モデルのフィールドは `GET /v2/models/{provider}/{model}/openapi.json` から読み取ります。この呼び出しには APIキーが必要です。スキーマが作成されているすべてのモデルについて、同じドキュメントが APIキーなしでこのサイトの `/router-schemas/{provider}/{model}.json` にも公開されています。このコピーは最後のドキュメント更新時に取得されたスナップショットであるため、両者が異なる場合はエンドポイントの内容が正式です。オペレーションの `requestBody` は入力の検証を記述しており、その `200` レスポンスは、スキーマが作成されている場合に出力の形状とメディアタイプを記述しています。`x-comfy-input-schema-authored` が false の場合、Router はモデル固有の事前検証なしで任意の JSON オブジェクトを受け入れます。プロバイダーの要件は引き続き適用されます。出力スキーマは結果を記述するものであり、Router は返されたプロバイダーのペイロードをそれらに対して検証しません。スキーマが作成されていない出力では、`application/json` ではなく `*/*` が使用される場合があります。デコードする前にレスポンスのコンテンツタイプを確認してください。

### RouterCostEstimate

この呼び出しにかかるコストを米ドルで事前に見積もったものです。価格はディスパッチ前に、Comfy のスタンダードなリスト価格で算出されます。ベンダーが報告するコストで課金されるモデルの場合は、ベンダーの公開価格表に基づいて算出されます。このベンダー報告のケースでは、`source: exact` が返されるのは、オプトインした少数のモデルに限られ、かつ公開価格表が金額を完全に決定できる場合のみです（価格を左右するすべてのフィールドが明示されているか、金額を変えようのないデフォルトのままである場合）。それ以外のベンダー報告の見積もりはすべて `estimated` となり、価格表で完全に決定できるはずのものも含まれます。いずれの場合も、実行の完了後にはベンダーが報告する金額で課金され、見積もりの数値がそのまま請求されることはありません。契約や顧客固有のレートは反映されません。個別価格を交渉したワークスペースにはリスト価格が見積もられ、契約レートで課金されます。その場合の `source: exact` はリスト価格に対して正確という意味であり、そのワークスペースの請求額が正確という意味ではありません。これは最終的な請求額ではありません。支払うのは、ワークスペースの使用量および請求記録に確定した請求額です。実行後に報告される `X-Comfy-Credits-Used` は事後に丸められた数値であり、領収書ではありません。`source` はその数値をどこまで信頼できるかを示します。`exact` は `amount` を持ちます。`free` は `amount` が "0" です（レートカードがこのリクエストをゼロで価格設定しています）。`estimated` は `min_amount` と `max_amount` を持ち、`amount` は持ちません。`unknown` はどちらも持たず、`reason` を持ちます。`amount` が存在しないことを無料と読み取らないでください。価格のロックではありません。`pricing_as_of` を参照してください。

**フィールド**

<ResponseField name="source" type="string" required>
  `exact` | `estimated` | `free` | `unknown`。これ以外の値は `unknown` として扱ってください。`exact` と `estimated` はいずれも見積もりを示すものであり、どちらも最終的な請求額ではありません。`free` は、レートカードがこのリクエストをゼロで価格設定していることを意味するため、`amount` は "0" です。`unknown` には金額が含まれません。
</ResponseField>

<ResponseField name="currency" type="string" required>

</ResponseField>

<ResponseField name="amount" type="string">
  推定コストをドル建ての10進文字列で表したもの（例: "0.04"）。最大8桁の小数部を持ち、指数表記は使用しません。課金対象の1セント未満の価格が "0" として出力されることはなく、"0" になるのは `free` の見積もりのみです。`source` が `exact` または `free` の場合にのみ存在します。最終的な請求額ではありません。最終的な請求額は、ワークスペースの使用量および請求記録に確定した金額です。
</ResponseField>

<ResponseField name="min_amount" type="string">

<ResponseField name="pricing_as_of" type="string" required>
  この見積もりの価格算出に使用したレートカードを取得した日時。見積もりは価格のロックではありません。実行は、評価時点で有効なレートで課金され、この時点のレートではありません。ベンダーの公開価格表から取得した `estimated` の見積もり（ベンダーが報告するコストで課金されるモデル）では、代わりにその価格表を読み取った日付が入ります。課金対象の数量が公開されたベンダーのスケジュールから予測され、その後レートカードで価格設定される見積もりの場合は、そのスケジュールの読み取り日とカードの取得時刻のうち古い方が入ります（`exact` の回答でも `estimated` の回答でも同様です。ベンダーが報告するクレジットで課金されるモデルは `estimated` のケースです）。レートカードが一切読み取られなかった場合（`reason: pricing_unavailable`、`byok`、またはどのカードからも価格を算出できない `not_quotable` の呼び出し）は、見積もりに回答した日時になります。

<ResponseField name="reason" type="string">

### RouterErrorResponse

認証、アクセス、モデル検索、クォータ、プロバイダーのトランスポート失敗に対するエラーボディです。

**フィールド**

<ResponseField name="detail" type="string" required>
  失敗の人間が読める説明で、エンドユーザーに提示しても安全です。機械解析はされません。代わりに `error_type` で分岐してください。退役したモデルに対する `model_not_found` では、後継モデルが記録されていて呼び出し元から参照できる場合、`detail` は `<id> was retired on <YYYY-MM-DD>; use <successor>` となり、そうでない場合は通常の候補リストの代わりに `<id> was retired on <YYYY-MM-DD>` だけになります。ここで示される後継モデルは常に、呼び出しの向き先を変更できる有効なカタログ ID です。提供終了日がまだ将来であるモデルは退役していません。`GET /v2/models` に引き続き表示され、その日付までは実行可能なままです。`detail` の他の部分と同様、この退役に関する文言は表示用であり、互換性の保証はありません。機械解析されないというルールには、文書化された 2 つの例外があります。`POST /v2/models/{provider}/{model}` では、`409` が `invalid_input` バケットを共有する 3 つの無関係な条件に対して返され、それらを区別するのは `detail` だけです。`detail` が「this request's `image` selects the edit operation」で始まる場合はマルチパートの `model_provider` 拒否であり、`detail` が `this request resolved a BYOK credential` で始まる場合は BYOK の `model_provider` 拒否です。どちらも新しい `Idempotency-Key` では解消されません。そのルート上の他の `invalid_input` `409` はキーの競合です。どちらの接頭辞も安定した契約用語であり、マッチングしてもかまいません。他のどこでも、`detail` に基づく分岐に互換性の保証はありません。
</ResponseField>

<ResponseField name="error_type" type="RouterErrorType" required>
  Router の失敗を表す粗い機械可読なバケットで、`X-Comfy-Error-Type` レスポンスヘッダーにも反映されるため、呼び出し元はボディを解析せずに分岐できます。この集合は 20 個の値で閉じています。6 つのリクエストレベルのバケット `invalid_input`、`content_policy_violation`、`provider_error`、`provider_timeout`、`insufficient_credits`、`model_not_found` に加え、トランスポートレベルの `unauthorized`、`forbidden`、`concurrency_limit_exceeded`、`client_disconnected`、`internal_error`、`deadline_exceeded`、`not_enabled`、`service_unavailable`、`rate_limited`、`cancelled`、`queue_timeout`、`request_not_found`、`queue_backlog_full`、`result_expired` です。「閉じている」とは、今日文書化されている時点での集合を説明するものであり、永久に成立する上限ではありません。集合は増えることが想定されているため、これは意図的にプレーンな文字列であり `enum` ではありません。そのためクライアントは、認識できない値を `internal_error` として扱う必要があり、上記のリストを網羅的に switch して次の追加で壊れてはいけません。

  型: [`RouterErrorType`](#routererrortype)
</ResponseField>

<ResponseField name="upstream_detail" type="string">
  `invalid_input` 拒否に対する、長さが制限されサニタイズされた理由です。同期ルートでは、モデルプロバイダーが示した理由であり、`error_type` が `invalid_input` で、`X-Comfy-Upstream-Status` がプロバイダーの `4xx` または `2xx` の場合にのみ存在します。つまり、プロバイダーがリクエストを不正な形式として拒否し、その理由を述べた場合です。通常、そのステータスは `4xx` です。成功エンベロープ内で拒否された生成を報告するプロバイダーでは `2xx` になります（BytePlus の失敗タスクポーリングは HTTP `200` で、理由がボディに含まれます）。プロバイダーの `5xx`、トランスポート失敗、コンテンツポリシー拒否、Router 自身に関する拒否を含む他のすべての失敗では存在せず、`X-Comfy-Upstream-Detail` ヘッダーを反映します。`invalid_input` で終了した実行のキュー中のコレクト（`GET /v2/models/{provider}/{model}/requests/{request_id}`）は、最初のコレクトでこのフィールドに同じ理由を含み、その後リクエストから削除されます。後で行うコレクトは通常、それを含まない同じ `error_type` と `detail` を返すため、最初のコレクトから読み取ってください。その読み取りではどちらのヘッダーも送信されません。キュー中のコレクトはまた、Router がリクエストをプロバイダーに送信する前に拒否し、理由を 1 文で述べられる場合、Router 自身の理由にもこのフィールドを使用します。同期ルートではそれを `detail` で返します。個々のフィールドを名指しする拒否には何も含まれません。
</ResponseField>

<ResponseField name="refusal_subject" type="string">
  コンテンツポリシー拒否がどの入力または出力に関するものかを示す、Router レベルの閉じた語彙です。`input`、`output`、`input_text`、`input_image`、`input_video`、`input_audio`、`output_text`、`output_image`、`output_video`、`output_audio`。プロバイダーがモダリティを名指ししなかった場合、裸の `input` / `output` 値がどちら側かを示します。`error_type` が `content_policy_violation` で、プロバイダーが拒否された対象を機械可読コードで名指しした場合にのみ存在し、それ以外では存在しません。プロバイダーのテキストは決して含みません。現在、BytePlus、Runway、BFL、Gemini、Veo、Vertex、xAI、Wan の拒否、および MiniMax Router の Nano Banana レッグの Gemini 拒否について名指しされます。拒否がどちら側に関するものかを示さないプロバイダーでは存在しません。`X-Comfy-Refusal-Subject` ヘッダーを反映します。
</ResponseField>

<ResponseField name="denied_reason" type="string">

</ResponseField>

<ResponseField name="billed_workspace" type="RouterBilledWorkspace">
  `RouterErrorResponse.billed_workspace` は、拒否された呼び出しが請求していたはずのウォレットです。「どのウォレットが空か」に答えるものであり、呼び出し元の UI で現在選択されているワークスペースとは限りません。また、資金のあるチームが開かれている間でも、チームメンバーの個人クレデンシャルはここでその個人ウォレットを示します。`denied_reason` と同時にのみ存在します。

  型: [`RouterBilledWorkspace`](#routerbilledworkspace)
</ResponseField>

<ResponseField name="credential_kind" type="string">

</ResponseField>

<ResponseField name="next_cursor" type="RouterPageCursor">
  Router リストへの不透明なカーソルです。サーバーが生成し、往復させることだけを目的としています。オフセットでもモデル ID でもなく、順序付けもされておらず、カタログの再構築をまたいで安定もしないため、パースすること、インクリメントすること、取得元の走査を超えて永続化することは、いずれも契約の範囲外です。オフセットではなくカーソルを使うのは、カタログが変化し続けるリストだからです。オフセットによる走査では、走査の途中でエントリが追加または削除されると、気付かないうちにエントリがスキップされたり重複したりし、呼び出し元はそれが起きたことを判別できません。

  型: [`RouterPageCursor`](#routerpagecursor) -- `next_cursor` として返される不透明なカーソル、1〜512 文字
</ResponseField>

<ResponseField name="limit" type="integer" required>
  実際に提供されたページサイズ。最大値を超える `limit` を要求した場合は、拒否されるのではなく最大値に丸められるため、要求した値より小さくなることがあります。送信した数値ではなく、この数値でページネーションしてください。そうしないと、受け取っていない行を前提にしてしまいます。

  1〜100
</ResponseField>

**フィールド**

<ResponseField name="request_id" type="RouterQueueRequestId" required>

### RouterQueueRequestId

### RouterQueueStatus

キュー中の Router リクエストの状態。正確に3つの値を持ち、`RouterErrorType` とは異なり、これは閉じた `enum` です。なぜなら、2つのスキーマは意図的に逆方向に閉じられているからです。`RouterErrorType` は失敗を分類し、その集合は増えることが想定されています。そのため、認識されないバケットを厳密に拒否する生成済みクライアントは、何かがすでにうまくいかなかったときに最も失敗しやすくなります。これはライフサイクルであり、後で4番目の状態が追加されたライフサイクルは、`enum` として宣言されているかどうかにかかわらず、それに対して書かれたすべてのポーリングループにとって破壊的変更です。そのため、`enum` として宣言され、制約はクライアントが見える場所に記述されています。

型: `string`

**フィールド**

<ResponseField name="request_id" type="RouterQueueRequestId" required>
  キュー中の Router リクエスト 1 件の識別子。呼び出し側がポーリング、キャンセル、結果取得に使うハンドルです。

  Type: [`RouterQueueRequestId`](#routerqueuerequestid) -- `pattern: ^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`, uuid, 最大 36 文字

<ResponseField name="status" type="RouterQueueStatus" required>

</ResponseField>

<ResponseField name="queue_position" type="RouterQueuePosition">
  レスポンスが構成された瞬間に、このリクエストより前にキュー内にあるリクエストの数です。0 はこのリクエストが先頭であることを意味します。

  Type: [`RouterQueuePosition`](#routerqueueposition) -- 0 以上
</ResponseField>

<ResponseField name="error_type" type="RouterErrorType">
  成功しなかった `COMPLETED` リクエストにのみ存在し、その失敗を返すときに結果読み取りが `X-Comfy-Error-Type` に設定するのと同じ大まかな分類を保持します。これにより、成功したターミナルリクエストと、失敗またはキャンセル済みのリクエストを区別できます。どちらにも別個のターミナルステータスは存在しません。また、成功時には null ではなく存在しないため、その有無で分岐してください。

  Type: [`RouterErrorType`](#routererrortype)
</ResponseField>

**フィールド**

<ResponseField name="request_id" type="RouterQueueRequestId" required>

<ResponseField name="loc" type="array of any" required>
  問題のあるフィールドへのパス。最も外側のセグメントが先頭になります。たとえば `["body", "image_url"]`、または `["body", "images", 0]` のように、整数は配列のインデックスを指します。

<ResponseField name="msg" type="string" required>
  この 1 件の失敗について、人間が読める形で説明したもの。

<ResponseField name="type" type="string" required>
  この失敗の具体的で機械可読な理由。プロバイダーからそのまま変更されずに渡されます。型付き SDK の例外階層が分岐に使う値はこれであり、レスポンスヘッダーの `error_type` はその大まかな分類にすぎません。

</ResponseField>

<ResponseField name="input" type="RouterValidationErrorInput">
  問題のある入力値。呼び出し元が `loc` から再導出しなくても何が拒否されたかを確認できるよう、そのまま返されます。文字列、数値、ブール、配列、オブジェクト、null のいずれの JSON 型でもよいため、このスキーマはオブジェクトに絞り込まず、意図的に型なしのままにしています。プロバイダーが入力をそのまま返さない場合、このフィールドは存在しません。

</ResponseField>
