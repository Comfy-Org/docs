URL 形式を推奨します。base64 ペイロードはおよそ 4/3 に膨らみ、リクエストボディ全体は 100 MiB に制限されるため、インライン形式は約 75 MB のソース画像で上限に達します。URL はそれを完全に回避します。この説明の最後に記載されている画像ごとおよびリクエストごとのメディア上限はボディ上限よりも厳しいため、実際のサイズの画像ではまずそちらに達します。
URL は認証情報なしで解決できなければなりません。Router はサーバー側で取得し、リクエストに呼び出し元の認証情報を付けません。そのため、署名がクエリ文字列にあるような署名付き URL がサポートされる形式です。`/api/assets/{id}/content` のような認証が必要なエンドポイントは、画像ではなく 401 を Router に返します。その URL はご自身でリクエストし、リダイレクト先の署名付き URL を渡してください。
フェッチはオープンなインターネットではなく、名前を付けた一連のホストに限定されます。同じリストは、送信した URL だけでなくすべてのリダイレクト ホップにも再適用されます。したがって、それ以外のホストの URL、またはリスト外にリダイレクトする URL は、プロバイダーに接続する前に拒否されます。現在このリストは Comfy 自身のアセット配信のみです。つまり Comfy のアセットバケット配下の署名付き `storage.googleapis.com` URL であり、これは `/api/assets/{id}/content` がリダイレクトする形式です。パートナーの CDN や通常の https ホストはリストにありません。
2 つの拡張が展開中で、どちらも今日はデフォルトでオフです。それらは 1 つの切り替えの背後で提供され、同時に有効になります。したがって、以下はすべてまだ依存して構築すべきものではなく、今後提供されるものとして扱ってください。どちらかに依存する前に確認してください。
1 つ目は、`POST /customers/storage` がアップロード先として署名するバケットです。展開がお使いの環境に届くまで、そのエンドポイントからのアップロード URL はここで拒否されます。バケットが Comfy 自身のものでホストも同じであってもです。したがって「Comfy にアップロードしてから URL を渡す」はまだ機能せず、機能する形式は `/api/assets/{id}/content` がリダイレクトする署名付き URL です。
2 つ目は、全員に一度にではなくアカウントごとに有効になります。これらのホストの背後にあるバケットは弊社のものではなくお客様のものであるためです。上記の切り替えがオンになっていても、サードパーティの受信メディアが有効化されていないアカウントは拒否され、ホストがサポートされていないと告げられるのではなく、その旨をその言葉で伝えられます。お客様の Comfy 担当者にアカウントでの有効化を依頼してください。これにより、以下のサードパーティのオブジェクトストレージ ホストも追加で許可されます。ここではバケットはお客様のものであり、Router はその所有権を主張しません: Cloudflare R2（`<account>.r2.cloudflarestorage.com`、`<id>.r2.dev`）、Amazon S3（`s3.amazonaws.com` および `s3.<region>.amazonaws.com`、パス形式または `<bucket>.` を前に付ける形式のいずれか）、Azure Blob Storage（`<account>.blob.core.windows.net`）、Alibaba Cloud OSS（`<bucket>.oss-<region>.aliyuncs.com`、`oss-accelerate` エンドポイントを含む）。これらは特にオブジェクトストレージのエンドポイントです。同じプロバイダードメイン上の汎用エンドポイント（例えば Alibaba Function Compute のトリガー）はリストになく、拒否されます。
