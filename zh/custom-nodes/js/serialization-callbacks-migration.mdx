Configuring a root `LGraph` from serialized data now requires an active
Pinia instance. `LGraph.configure()` clears and rebuilds the graph directly
against the ECS stores, so a test harness, worker, or standalone LiteGraph
consumer that calls `new LGraph(data)` or `graph.configure(data)` without an
active Pinia now fails outright instead of silently producing an empty
graph. This is the same requirement documented in
[Link registration migration](/zh/custom-nodes/js/link-registration-migration).

Extensions running in ComfyUI use the application's active Pinia instance.
Do not create or activate a separate Pinia instance from extension code.

`node.onConfigure`, `node.onSerialize`, `graph.onConfigure`, and
`graph.onSerialize` keep their existing signatures and firing order. For
connection-timing hooks see
[Connection callbacks migration](/zh/custom-nodes/js/connection-callbacks-migration); for
`node.widgets` and widget value storage see
[Widget system migration](/zh/custom-nodes/js/widgets-migration).

`onConfigure` now receives a shallow copy of the serialized data rather than
the caller's own object. Adding, removing, or reassigning top-level keys on the
callback argument does not change the caller's workflow JSON and is not
persisted. Nested objects (for example `inputs`, `pos`, `properties`) are still
shared with the caller, so mutating them in place still leaks; extensions that
relied on either kind of mutation must store custom state on `node.properties`
or `graph.extra` instead.

## 将自定义数据存放在 properties 或 extra 中

每个节点的扩展数据使用 `node.properties`，每个图的扩展数据使用 `graph.extra`。对于持久化数据，它们仍然是稳定且官方支持的扩展入口。

调用 `onSerialize` 和 `onConfigure` 时，`this` 绑定到活动的节点/图对象；传给回调的参数是序列化后的数据对象（`ISerialisedNode`/`ISerialisedGraph`），而不是活动的节点/图。由于 `this` 仍是活动对象，钩子可以改写它上面的任何字段，包括现在由 store 支撑的字段。不要用这些钩子覆盖核心字段：在 `onSerialize`/`onConfigure` 内部通过 `this` 写入会直接落到 store，没有自己的 schema、归属或撤销边界。

`onSerialize` 在前端把 `graph.extra` 和 `node.properties` 复制进数据对象之后运行，因此钩子添加到 `this.extra` 或 `this.properties` 的键不会出现在本次保存中。在 `onSerialize` 内部，请改为写入回调参数：图写 `data.extra`，节点写 `data.properties`。否则请在序列化开始之前更新 `graph.extra` 或 `node.properties`。

`onSerialize` 只持有一个回调，因此请保留其它扩展已经装好的钩子：

```js
const previous = graph.onSerialize
graph.onSerialize = function (data) {
  previous?.call(this, data)
  data.extra.myExtension = { version: 1 }
}
```

只有根图会运行 `onSerialize`。子图定义保存时不会在子图上调用钩子，因此请在保存工作流之前把子图数据写入 `subgraph.extra`。

钩子添加到 `data` 的自定义顶层键在 `LGraph.asSerialisable()` 中仍留在顶层。旧入口 `LGraph.serialize()` 会把它移到 `data.extensions` 下，并丢弃不是 JSON 兼容的值。工作流加载时，`onConfigure` 会再次在顶层收到该键。`extra` 下的键在两个入口中都保持原位。

## 序列化节点，而不是枚举属性

如果你的扩展通过枚举节点自身的属性来构建节点的序列化表示或调试表示，请将其切换为 `node.serialize()`。

`id`、`type`、`title`、`flags`、`mode`、`color`、`bgcolor`、`shape` 和 `showAdvanced` 现在是指向节点数据存储的访问器属性，不再是节点实例自身的自有数据属性。`Object.keys(node)`、`for...in` 和 `{ ...node }` 不再暴露这些字段，但直接读取和写入（`node.title`、`node.mode = ...`）仍可照常工作。`inputs`、`outputs` 和 `widgets` 仍可被自有枚举，因此展开与枚举仍会取到这三项。

关于 widget 级别的 `serializeValue`，它属于一个独立的序列化层，构建的是 API prompt 载荷，而非工作流 JSON，请参阅
[Widget 系统迁移](/zh/custom-nodes/js/widgets-migration)。
