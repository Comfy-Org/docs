[PR #2666](https://github.com/Comfy-Org/ComfyUI/pull/2666) меняет модель выполнения с рекурсивной модели, идущей от конца к началу, на топологическую сортировку от начала к концу. Хотя большинство пользовательских узлов должны по-прежнему «просто работать», эта страница призвана служить руководством для создателей пользовательских узлов по тем вещам, которые *могут* сломаться.

## Критические изменения
### Манки-патчинг

Любой код, который применял манки-патчинг к модели выполнения, скорее всего, перестанет работать. Обратите внимание: производительность выполнения с этим PR выше, чем с самыми популярными манки-патчами, поэтому многие из них станут ненужными.

### Валидация необязательных входов

До этого PR фактически валидировались только узлы, которые были подключены к выходам исключительно через цепочку входов `"required"`. Если у вас были пользовательские узлы, которые всегда подключались только к входам `"optional"`, раньше вы не видели, что они не проходят валидацию.

<Tip>Если выходы ваших узлов уже могли подключаться к входам `"required"`, маловероятно, что что-либо из этого раздела относится к вам. В первую очередь это касается авторов пользовательских узлов, которые используют пользовательские типы и работают исключительно со входами `"optional"`.</Tip>

Ниже перечислены некоторые причины, по которым вы можете не пройти валидацию, а также рекомендуемые решения:

- Использование зарезервированных [дополнительных параметров](/custom-nodes/backend/datatypes#additional-parameters) вроде `min` и `max` для типов, которые нельзя сравнивать (например, словарей), чтобы настроить пользовательские виджеты.
    - Замените используемые дополнительные параметры на незарезервированные ключи вроде `uiMin` и `uiMax`. *(Рекомендуемое решение)*
        ```python
        @classmethod
        def INPUT_TYPES(cls):
            return {
                "required": {
                    "my_size": ("VEC2", {"uiMin": 0.0, "uiMax": 1.0}),
                }
            }
        ```

    - Определите пользовательскую функцию [VALIDATE_INPUTS](/custom-nodes/backend/server_overview#validate_inputs), которая принимает этот вход, чтобы пропустить его валидацию. *(Быстрое решение)*
        ```python
        @classmethod
        def VALIDATE_INPUTS(cls, my_size):
            return True
        ```

- Использование составных типов (например, `CUSTOM_A,CUSTOM_B`)
    - (Если используется как выход) Определите и используйте обёртку вроде `MakeSmartType`, [показанную здесь в модульных тестах PR](https://github.com/Comfy-Org/ComfyUI/pull/2666/files#diff-714643f1fdb6f8798c45f77ab10d212ca7f41dd71bbe55069f1f9f146a8f0cb9R2)
        ```python
        class MyCustomNode:

            @classmethod
            def INPUT_TYPES(cls):
                return {
                    "required": {
                        "input": (MakeSmartType("FOO,BAR"), {}),
                    }
                }

            RETURN_TYPES = (MakeSmartType("FOO,BAR"),)

            # ...
        ```
    - (Если используется как вход) Определите пользовательскую функцию [VALIDATE_INPUTS](/custom-nodes/backend/server_overview#validate_inputs), которая принимает аргумент `input_types`, чтобы валидация типов пропускалась.
        ```python
        @classmethod
        def VALIDATE_INPUTS(cls, input_types):
            return True
        ```
    - (Поддерживает оба варианта, удобно) Определите и используйте декоратор `@VariantSupport`, [показанный здесь в модульных тестах PR](https://github.com/Comfy-Org/ComfyUI/pull/2666/files#diff-714643f1fdb6f8798c45f77ab10d212ca7f41dd71bbe55069f1f9f146a8f0cb9R15)
        ```python
        @VariantSupport
        class MyCustomNode:

            @classmethod
            def INPUT_TYPES(cls):
                return {
                    "required": {
                        "input": ("FOO,BAR", {}),
                    }
                }
            
            RETURN_TYPES = (MakeSmartType("FOO,BAR"),)

            # ...
        ```

- Использование списков (например, `[1, 2, 3]`) как констант в определении графа (например, чтобы представить константный вход `VEC3`). Раньше для этого потребовалось бы расширение фронтенда. Раньше списки ровно из `2` элементов всё равно не проходили бы проверку: они рассматривались бы как нарушенные соединения.
    - Оберните списки в словарь вроде `{ "value": [1, 2, 3] }`

### Порядок выполнения

Порядок выполнения всегда менялся в зависимости от того, какие узлы имеют какие ID, но теперь он может меняться и в зависимости от того, какие значения кэшированы. В целом порядок выполнения следует считать недетерминированным и подверженным изменениям (сверх того, что задаётся структурой графа).

Не полагайтесь на порядок выполнения.

## Новый функционал

### Изменения в валидации

В функцию `VALIDATE_INPUTS` добавлен ряд возможностей, чтобы уменьшить влияние [валидации необязательных входов](#валидация-необязательных-входов), описанной выше.

- Теперь для входов, которые получает функция `VALIDATE_INPUTS`, стандартная валидация пропускается.
- Функция `VALIDATE_INPUTS` теперь может принимать `**kwargs`, что означает, что все входы считаются проверенными создателем узла.
- Функция `VALIDATE_INPUTS` может принимать вход с именем `input_types`. Этот вход будет словарём, сопоставляющим каждый вход (прикреплённый через ссылку) с типом присоединённого выхода. При наличии этого аргумента валидация типов для входов узла пропускается.

Подробнее можно прочитать в разделе [VALIDATE_INPUTS](/custom-nodes/backend/server_overview#validate_inputs).

### Ленивое вычисление

Входы можно вычислять лениво (то есть вы можете подождать и проверить, нужны ли они, прежде чем вычислять присоединённый узел и всех его предков). Дополнительные сведения см. в разделе [Ленивое вычисление](/custom-nodes/backend/lazy_evaluation).

### Развёртывание узлов

Во время выполнения узлы могут развёртываться в подграф узлов. Именно это позволяет реализовать циклы (через хвостовую рекурсию). Дополнительные сведения см. в разделе [Развёртывание узлов](/custom-nodes/backend/expansion).
