Вводная информация о [Comfy SDKs](/ru/development/api-development/sdks) и [Comfy API v2](/api-reference/v2/overview), к которым они обращаются. Ничего из этого не нужно для работы с SDK. Прочитайте, если вы решаете, строить ли на новом API или на существующих.

## Зачем нужен новый API

Вы уже можете управлять ComfyUI по HTTP, вызывая `/prompt` и `/history`. Эти эндпоинты существуют для обслуживания веб-интерфейса ComfyUI, и построение на них означает зависимость от внутренних механизмов, которые вам никогда не гарантировали. API v2 добавляет три вещи, которых они не могут вам дать.

**Обязательство.** v2 версионируется, документируется и поддерживается. В v2 изменения только добавляются; всё, что нарушает совместимость, выйдет как v3. Новые релизы ComfyUI не сломают вашу интеграцию.

**Переносимость.** Одинаковое поведение при работе с локальным ComfyUI, с Comfy Cloud и с развёртыванием Comfy API. Тот же код, другой базовый URL.

**Форма, которая выдерживает продакшен.** Долговечные идентификаторы задач, идемпотентная отправка, типизированные ошибки, нормализованные выходы и настоящий механизм обратного давления вместо того, чтобы каждая интеграция заново изобретала все пять поверх `prompt_id` и `/history`.

## Почему не обернуть уже существующие эндпоинты

Потому что они рассчитаны на один экземпляр ComfyUI, выполняющий один рабочий процесс за раз, и это допущение встроено в `prompt_id`, `/history` и протокол websocket.

API v2 на это не опирается. Множество рабочих процессов, выполняемых одновременно, каждый со своим постоянным ID задачи, здесь является обычным случаем, а не исключением.

## Сначала опрос, поток для прогресса

Каждая возможность в v2 доступна через обычные GET-запросы. `GET /api/v2/jobs/{id}` возвращает текущий статус, последний снимок прогресса и все выходы, зафиксированные к этому моменту. Это авторитетное представление задачи, и оно остаётся доступным до наступления `expires_at` задачи.

Поток SSE по адресу `GET /api/v2/jobs/{id}/events`, доступный как `job.events()` в обоих SDK, это живое дополнение поверх описанного. Используйте его для отрисовки индикатора прогресса. Не используйте его как источник истины: он не содержит идентификаторов событий, не имеет курсора возобновления, а кадры, отправленные пока вы были отключены, теряются.

Две причины, почему авторитетный путь это опрос, а не поток или вебхук:

- Рабочие процессы могут выполняться долго. Соединение, моргнувшее на три секунды, не должно стоить вам результата.
- Вебхуки хорошо работают для сервиса с публичным адресом. Они не подходят для плагина Blender на чьём-то компьютере, который не слушает порт, и не должны подходить.

Практический эффект в том, что каждый шаг можно возобновить. Если ваш процесс упадёт посреди задачи, вы можете вернуться через час, и `GET /api/v2/jobs/{id}` всё ещё будет содержать статус и выходы. Другие транспорты могут быть добавлены позже для случаев, которые им подходят; этот работает везде.

## Связь с существующими API

Существующие API, включая [Cloud API](/ru/development/cloud/overview), продолжат работать. `/prompt`, `/history`, `/ws` и остальные эндпоинты продолжают работать. Если ваша интеграция работает сегодня, ничего из этого её не сломает. Оба варианта существуют параллельно.

| | Comfy API v2 | Существующие API |
|---|---|---|
| **Совместимость** | Версионируется. В пределах v2 только аддитивные изменения | Нет гарантии совместимости между релизами |
| **Модель параллелизма** | Много заданий одновременно, у каждого постоянный ID | Один экземпляр, один рабочий процесс за раз |
| **Работает на** | Comfy Cloud, развёртывания Comfy API и самостоятельно размещённый ComfyUI, единый контракт | Cloud API и ComfyUI Server API различаются |
| **Официальные клиенты** | SDK для Python и TypeScript | Нет |
| **Лучше всего подходит для** | Новых интеграций | Интеграций, которые уже работают |

## Объём первой версии

Одна задача, но как следует: запустить рабочий процесс и получить результаты. Загрузить входы, отправить граф в формате API, наблюдать за выполнением, получить выходы.

Это весь объём, и так задумано. Сохранённых рабочих процессов, управления библиотекой моделей, интроспекции узлов и именованных параметров рабочих процессов здесь пока нет. Мы предпочитаем выпустить небольшую поверхность API, которую действительно сможем поддерживать при любом способе развёртывания ComfyUI, а не большую, которая держится только в одном из них. Дальше она будет расти.

## Локальный прокси

ComfyUI при самостоятельном размещении работает с v2 через [comfy-api-proxy](https://github.com/Comfy-Org/comfy-api-proxy): он запускается вместе с вашим экземпляром и предоставляет контракт v2, располагаясь перед ним. Прокси имеет открытый исходный код. Инструкции по настройке см. в [руководстве по API Proxy](/ru/development/comfyui-server/api-proxy).

## Почему сначала Python и TypeScript

Именно здесь был спрос, когда мы спрашивали людей, уже масштабно использующих ComfyUI. Оба SDK опираются на один и тот же задокументированный HTTP-контракт, поэтому любой язык уже сейчас может взаимодействовать с API. Если вы хотите официальный SDK на другом языке, сообщите нам в канале `#developer-platform` в [нашем Discord](https://discord.com/invite/comfyorg).
