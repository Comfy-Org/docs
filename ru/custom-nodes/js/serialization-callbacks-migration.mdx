Для настройки корневого `LGraph` из сериализованных данных теперь требуется активный
экземпляр Pinia. `LGraph.configure()` очищает и перестраивает граф напрямую
через хранилища ECS, поэтому тестовый стенд, worker или автономный потребитель LiteGraph,
который вызывает `new LGraph(data)` или `graph.configure(data)` без
активного Pinia, теперь сразу завершается с ошибкой, а не молча создаёт пустой
граф. Это то же требование, что описано в разделе
[Миграция регистрации ссылок](/ru/custom-nodes/js/link-registration-migration).

Расширения, работающие в ComfyUI, используют активный экземпляр Pinia приложения.
Не создавайте и не активируйте отдельный экземпляр Pinia из кода расширения.

`node.onConfigure`, `node.onSerialize`, `graph.onConfigure` и
`graph.onSerialize` сохраняют существующие сигнатуры и порядок вызова. О
хуках, связанных с моментом соединения, см.
[Миграция колбэков соединений](/ru/custom-nodes/js/connection-callbacks-migration); о
`node.widgets` и хранении значений виджетов см.
[Миграция системы виджетов](/ru/custom-nodes/js/widgets-migration).

`onConfigure` теперь получает поверхностную копию сериализованных данных, а не
собственный объект вызывающего кода. Добавление, удаление или переназначение
ключей верхнего уровня в аргументе обратного вызова не изменяет JSON рабочего
процесса вызывающего кода и не сохраняется. Вложенные объекты (например,
`inputs`, `pos`, `properties`) по-прежнему используются совместно с вызывающим
кодом, поэтому изменение их на месте всё ещё приводит к утечке; расширения,
которые полагались на любой из этих видов изменения, должны вместо этого хранить пользовательское состояние в `node.properties` или `graph.extra`.

## Храните пользовательские данные в properties или extra

Используйте `node.properties` для данных расширения на уровне отдельного узла и `graph.extra` для данных расширения на уровне отдельного графа. Эти поверхности остаются стабильными и предназначенными для расширения при сохранении данных.

`onSerialize` и `onConfigure` вызываются с привязкой `this` к живому
объекту узла/графа; аргумент, передаваемый в колбэк, представляет сериализованный
объект данных (`ISerialisedNode`/`ISerialisedGraph`), а не живой узел/граф.
Поскольку `this` по-прежнему является живым объектом, хук может изменять любое поле в нём,
включая поля, которые теперь привязаны к хранилищу. Не используйте эти хуки для
перезаписи основных полей: запись через `this` изнутри
`onSerialize`/`onConfigure` попадает напрямую в хранилище, без
собственной схемы, принадлежности или границы отмены.

`onSerialize` выполняется после того, как фронтенд скопировал `graph.extra` и
`node.properties` в объект данных, поэтому ключ, который хук добавляет в
`this.extra` или `this.properties`, отсутствует в текущем сохранении. Внутри
`onSerialize` вместо этого пишите в аргумент обратного вызова: `data.extra` для
графа, `data.properties` для узла. В противном случае обновите `graph.extra` или
`node.properties` до начала сериализации.

`onSerialize` хранит один колбэк, поэтому сохраните любой хук, который уже установило другое расширение:

```js
const previous = graph.onSerialize
graph.onSerialize = function (data) {
  previous?.call(this, data)
  data.extra.myExtension = { version: 1 }
}
```

`onSerialize` выполняется только для корневого графа. Определения подграфов
сохраняются без вызова хука на подграфе, поэтому сохраняйте данные подграфа в `subgraph.extra`
до сохранения рабочего процесса.

Пользовательский ключ верхнего уровня, который хук добавляет в `data`, остаётся на верхнем уровне в
`LGraph.asSerialisable()`. Устаревшая точка входа `LGraph.serialize()` вместо этого переносит его
в `data.extensions` и опускает значения, несовместимые с
JSON. При загрузке рабочего процесса `onConfigure` снова получает ключ на
верхнем уровне. Ключи внутри `extra` сохраняют своё место в обеих точках входа.

## Сериализовать узлы вместо перечисления свойств

Если ваше расширение строит сериализованное или отладочное представление узла, перечисляя его собственные свойства, переключите его на `node.serialize()`.

`id`, `type`, `title`, `flags`, `mode`, `color`, `bgcolor`, `shape` и `showAdvanced` теперь являются свойствами-аксессорами поверх хранилища данных узла, а не собственными свойствами данных экземпляра узла. `Object.keys(node)`, `for...in` и `{ ...node }` больше не показывают эти поля, хотя прямое чтение и запись (`node.title`, `node.mode = ...`) продолжают работать без изменений. `inputs`, `outputs` и `widgets` остаются собственными перечисляемыми свойствами, поэтому spread/перечисление по-прежнему захватывает эти три.

Для `serializeValue` на уровне виджетов, отдельного слоя сериализации, который формирует payload API-промпта, а не JSON рабочего процесса, см. [Миграция системы виджетов](/ru/custom-nodes/js/widgets-migration).
