<Info>
Определения узлов на этой странице используют устаревшую схему V1 (`INPUT_TYPES` / `RETURN_TYPES`), которая по-прежнему полностью поддерживается. Новые узлы можно писать и по современной схеме V3 (`io.ComfyNode` с `define_schema` и функцией `comfy_entrypoint`) — именно так написан поставляемый [`custom_nodes/example_node.py.example`](https://github.com/comfyanonymous/ComfyUI/blob/master/custom_nodes/example_node.py.example). Различия и порядок миграции описаны в [руководстве по миграции на V3](/ru/custom-nodes/v3_migration).
</Info>

### Простой пример

Ниже код узла Invert Image, который даёт общее представление о ключевых концепциях разработки пользовательских узлов.

```python
class InvertImageNode:
    @classmethod
    def INPUT_TYPES(cls):
        return {
            "required": { "image_in" : ("IMAGE", {}) },
        }

    RETURN_TYPES = ("IMAGE",)
    RETURN_NAMES = ("image_out",)
    CATEGORY = "examples"
    FUNCTION = "invert"

    def invert(self, image_in):
        image_out = 1 - image_in
        return (image_out,)
```

### Основные свойства

Каждый пользовательский узел — это класс Python со следующими ключевыми свойствами:

#### INPUT_TYPES

`INPUT_TYPES`, как следует из названия, определяет входы узла. Метод возвращает `dict`,
в котором _обязательно_ должен быть ключ `required`, а также _могут_ быть ключи `optional` и/или `hidden`. Единственное отличие
между обязательными (`required`) и необязательными (`optional`) входами в том, что необязательные входы можно оставить неподключёнными.
Подробнее о `hidden`-входах см. [Скрытые входы](./more_on_inputs#скрытые-входы).

Значением каждого ключа служит ещё один `dict`, в котором пары ключ-значение задают имена и типы входов.
Типы определяются `tuple`, первый элемент которого задаёт тип данных,
а второй — `dict` дополнительных параметров.

Здесь у нас один обязательный вход с именем `image_in` типа `IMAGE` и без дополнительных параметров.

Обратите внимание, что, в отличие от нескольких следующих атрибутов, этот `INPUT_TYPES` — это `@classmethod`. Это нужно,
чтобы варианты в выпадающих виджетах (например, имя загружаемого чекпойнта) можно было
вычислять в Comfy во время выполнения. Об этом подробнее ниже. {/* TODO link when written */}

#### RETURN_TYPES

`tuple` из `str`, задающий типы данных, которые возвращает узел.
Если у узла нет выходов, всё равно нужно указать `RETURN_TYPES = ()`
<Warning>Если у вас ровно один выход, не забудьте запятую: `RETURN_TYPES = ("IMAGE",)`.
Она нужна, чтобы Python создал `tuple`</Warning>

#### RETURN_NAMES

Имена для подписей выходов. Параметр необязательный; если его пропустить, именами будут `RETURN_TYPES` в нижнем регистре.

#### CATEGORY

Где узел будет находиться в меню **Add Node** в ComfyUI. Подменю задаются путём, например `examples/trivial`.

#### FUNCTION

Имя функции Python в классе, которая вызывается при выполнении узла.

Функция вызывается с именованными аргументами. Передаются все `required` (и `hidden`) входы;
`optional` входы передаются только если они подключены, поэтому задайте для них значения по умолчанию в определении функции
(или примите их через `**kwargs`).

Функция возвращает tuple, соответствующий `RETURN_TYPES`. Это нужно, даже если ничего не возвращается (`return ()`).
И снова: если у вас только один выход, не забудьте запятую `return (image_out,)`!

### Дополнительные средства управления выполнением

Сильная сторона Comfy в том, что он кеширует выходы
и выполняет только те узлы, результат которых может отличаться от прошлого запуска.
Это заметно ускоряет многие рабочие процессы.

По сути это работает так: сначала определяются узлы, которые выдают результат (они, в частности узлы Image Preview и Save Image, выполняются всегда), а затем
в обратном порядке выясняется, какие узлы дают данные, которые могли измениться с прошлого запуска.

В этом процессе помогают две необязательные возможности пользовательского узла.

#### OUTPUT_NODE

По умолчанию узел не считается выходным. Укажите `OUTPUT_NODE = True`, чтобы объявить его выходным.

#### IS_CHANGED

По умолчанию Comfy считает, что узел изменился, если изменился любой его вход или виджет.
Обычно это верно, но иногда это поведение нужно переопределить: например, если узел использует случайное
число (и не задаёт seed — в этом случае лучше добавить вход seed, чтобы пользователь управлял воспроизводимостью и не запускал лишние вычисления), или загружает вход, который мог
измениться извне, или иногда игнорирует входы (и тогда не нужно выполняться только из-за их изменения).

<Warning>Несмотря на название, IS_CHANGED не должен возвращать `bool`</Warning>

`IS_CHANGED` получает те же аргументы, что и основная функция, заданная в `FUNCTION`, и может вернуть любой
объект Python. Этот объект сравнивается с возвращённым в прошлый запуск (если он был), и узел
считается изменившимся, если `is_changed != is_changed_old` (код находится в `execution.py`, если нужно копнуть глубже).

Поскольку `True == True`, узел, который возвращает `True` будто бы «изменился», на самом деле будет считаться неизменившимся! Уверен, это бы
исправили в коде Comfy, если бы это не могло сломать существующие узлы.

Чтобы узел всегда считался изменившимся (чего по возможности стоит избегать, поскольку это
мешает Comfy оптимизировать выполнение), верните `float("NaN")`. Это значение `NaN` не равно
ничему, даже другому `NaN`.

Хороший пример настоящей проверки изменений — код встроенного узла LoadImage, который загружает изображение и возвращает хеш
```python
    @classmethod
    def IS_CHANGED(s, image):
        image_path = folder_paths.get_annotated_filepath(image)
        m = hashlib.sha256()
        with open(image_path, 'rb') as f:
            m.update(f.read())
        return m.digest().hex()
```

#### SEARCH_ALIASES

Необязательно. Список альтернативных имён, по которым пользователи могут искать этот узел.
Он попадает в ответ API `/object_info` как `search_aliases`.

```python
SEARCH_ALIASES = ["text concat", "join text", "merge strings"]
```

### Другие атрибуты

Есть ещё три атрибута, которые меняют стандартную обработку узла в Comfy.

#### INPUT_IS_LIST, OUTPUT_IS_LIST

Они управляют последовательной обработкой данных и описаны [ниже](./lists).

### VALIDATE_INPUTS

Если в классе определён метод `VALIDATE_INPUTS`, он вызывается до начала выполнения рабочего процесса.
`VALIDATE_INPUTS` должен вернуть `True`, если входы корректны, или сообщение (в виде `str`) с описанием ошибки (это предотвратит выполнение).

#### Проверка констант
<Warning>Учтите, что `VALIDATE_INPUTS` получает только входы, заданные в рабочем процессе константами. Входы, полученные от других узлов, в `VALIDATE_INPUTS` *недоступны*.</Warning>

`VALIDATE_INPUTS` вызывается только с теми входами, которые запрашивает его сигнатура (их возвращает `inspect.getfullargspec(obj_class.VALIDATE_INPUTS).args`). Любые полученные так входы *не* проходят стандартные правила проверки. Например, во фрагменте ниже фронтенд применит указанные `min` и `max` входа `foo`, но бэкенд их не проверит.

```python
class CustomNode:
    @classmethod
    def INPUT_TYPES(cls):
        return {
            "required": { "foo" : ("INT", {"min": 0, "max": 10}) },
        }

    @classmethod
    def VALIDATE_INPUTS(cls, foo):
        # YOLO, anything goes!
        return True
```

Кроме того, если функция принимает `**kwargs`, она получит *все* доступные входы, и все они пропустят проверку, как если бы были указаны явно.

#### Проверка типов

Если метод `VALIDATE_INPUTS` получает аргумент `input_types`, ему передаётся словарь, где ключ — имя каждого входа, подключённого к выходу другого узла, а значение — тип этого выхода.

Когда этот аргумент присутствует, стандартная проверка типов входов полностью пропускается. Вот пример, использующий тот факт, что фронтенд позволяет указывать несколько типов:

```python
class AddNumbers:
    @classmethod
    def INPUT_TYPES(cls):
        return {
            "required": {
                "input1" : ("INT,FLOAT", {"min": 0, "max": 1000})
                "input2" : ("INT,FLOAT", {"min": 0, "max": 1000})
            },
        }

    @classmethod
    def VALIDATE_INPUTS(cls, input_types):
        # The min and max of input1 and input2 are still validated because
        # we didn't take `input1` or `input2` as arguments
        if input_types["input1"] not in ("INT", "FLOAT"):
            return "input1 must be an INT or FLOAT type"
        if input_types["input2"] not in ("INT", "FLOAT"):
            return "input2 must be an INT or FLOAT type"
        return True
```
