Rutas canónicas de Comfy Router, direccionadas por ID de modelo.

URL base: `https://api.comfy.org`

Todos los endpoints siguientes requieren autenticación. Envía `X-API-Key: <api-key>` o `Authorization: Bearer <jwt>`.

Las claves de API de Comfy también se pueden enviar como tokens Bearer. `X-API-Key` tiene prioridad cuando se proporcionan ambos encabezados de credenciales. Consulta [encabezados de autenticación](/es/development/comfy-router/headers#encabezados-de-la-solicitud) para ver la distinción entre clave y JWT y [la guía de inicio rápido](/es/development/comfy-router/quickstart) para conocer los requisitos de acceso.

**Ejecuta un modelo socio de forma síncrona mediante su ID de modelo canónico.**

**Parámetros**

<ParamField path="provider" type="RouterProviderSegment" required>
  Porción de proveedor del ID de modelo canónico `{provider}/{model}`.

  Tipo: [`RouterProviderSegment`](#routerprovidersegment) -- Slug alfanumérico, p. ej. `anthropic`, hasta 64 caracteres
</ParamField>

<ParamField path="model" type="RouterModelSegment" required>
  Porción de modelo del ID de modelo canónico `{provider}/{model}`.

  Tipo: [`RouterModelSegment`](#routermodelsegment) -- Slug alfanumérico, p. ej. `claude-opus-4-6`, hasta 128 caracteres
</ParamField>

<ParamField header="Idempotency-Key" type="string">
  Clave generada por quien llama que hace seguro reintentar una misma llamada lógica.

  1–255 caracteres
</ParamField>

<ParamField query="model_provider" type="string">
  Selecciona un proveedor alternativo para servir este modelo en lugar de su valor predeterminado actual; `fal`, `wavespeed`, `runware` y `higgsfield` son los alternativos, y `GET /v2/models/{provider}/{model}` informa cuáles de ellos admite un modelo dado. Sus rechazos se comprueban en un orden fijo, y los anteriores responden tanto si los posteriores lo harían como si no: un valor no reconocido (que no es un proveedor registrado en absoluto) se rechaza con `400`; luego, un proveedor alternativo en una solicitud cuyo cuerpo selecciona una operación multipart (una edición) se rechaza con `409` con `detail` que empieza por "this request's `image` selects the edit operation", pero solo cuando el traductor de ese proveedor para este modelo no puede servir la operación: un tramo cuyo traductor sí admite los medios continúa con normalidad; luego, cualquier proveedor alternativo en una solicitud que resolvió una credencial bring-your-own-key se rechaza con `409` con `detail` que empieza por `this request resolved a BYOK credential` (consulta esa respuesta), tanto si ese proveedor sirve este modelo como si no; luego, la compuerta propia del proveedor nombrado, que rechaza con `403` con `error_type: not_enabled` cuando ese proveedor no está habilitado para ti y con `503` con `error_type: service_unavailable` cuando la compuerta no se puede evaluar; y solo después de las cuatro se rechaza con `400` con `error_type: invalid_input` un proveedor real sin tramo para este modelo, la misma respuesta que un valor no reconocido. `fallback_provider` queda inerte en lugar de rechazarse en una solicitud bring-your-own-key, en una solicitud cuyo cuerpo selecciona una operación multipart y con `strict_mode=true`.
</ParamField>

<ParamField query="strict_mode" type="boolean">
  Solo tiene sentido junto con `model_provider`.

  Predeterminado: False
</ParamField>

<ParamField query="fallback_provider" type="string">
  Controla si Router reintenta esta llamada contra el otro proveedor registrado del modelo cuando el primer intento falla por un motivo atribuible a Router o al proveedor probado. Si se omite, o con cualquier valor distinto de `false`, el fallback permanece activo; `false` lo desactiva. Una respuesta de fallback exitosa incluye `X-Comfy-Router-Fallback-Provider`. En una solicitud que resolvió una credencial bring-your-own-key el fallback no está disponible diga lo que diga este parámetro: el intento simplemente no se hace y el primer fallo te llega sin cambios, lo cual es inerte, no un rechazo: ningún `409` se origina aquí. Lo mismo ocurre, por la misma razón, en una solicitud cuyo cuerpo selecciona una operación multipart y con `strict_mode=true`: cada una vincula la llamada a un único proveedor que no se puede reproducir fielmente contra otro, así que el fallback simplemente se omite en lugar de rechazarse. Solo un `model_provider` explícito se rechaza con ese `409`, y, a diferencia de esta omisión incondicional, su `409` de multipart se aplica únicamente a un tramo cuyo traductor no puede servir la operación.
</ParamField>

<ParamField query="reject_unknown_fields" type="boolean">
  Opta por rechazar un campo de nivel superior del cuerpo de la solicitud que el esquema de entrada de este modelo no declara, en lugar de aceptarlo; los campos anidados no se comprueban, y no se rechaza nada para un modelo cuyo esquema permite campos no declarados o que no tiene esquema redactado, ni en un envío en cola enviado con `strict_mode=true`.

  Predeterminado: False
</ParamField>

**Cuerpo de la solicitud**

`application/json` -- [`RouterModelInput`](#routermodelinput) (requerido)

La entrada JSON nativa del modelo socio. Sin `model_provider`, la solicitud ejecuta el despacho nativo en el proveedor predeterminado del modelo y este cuerpo es el esquema nativo propio del modelo, reenviado sin cambios (`strict_mode` no tiene sentido ahí y no cambia nada). Con `model_provider` seleccionando un proveedor alternativo y `strict_mode=false` (el valor predeterminado), el cuerpo se traduce al esquema real de ese proveedor antes de enviarse: cualquier campo nativo que no se pueda expresar con exactitud se descarta y se revela mediante el encabezado `X-Comfy-Router-Dropped-Params` de la respuesta, nunca en silencio. Con `model_provider` seleccionando un proveedor alternativo y `strict_mode=true` no se ejecuta ninguna traducción: el cuerpo ya debe ser el esquema real propio de ese proveedor alternativo, no el nativo de este modelo (consulta `strict_mode`), y se reenvía sin cambios. Los campos del propio cuerpo también seleccionan qué operación ejecuta Router en un modelo que admite más de una: para un modelo de imagen editable, incluir una imagen de entrada lo cambia de texto a imagen a la operación imagen a imagen (edición), que puede facturarse con su propia tarifa; para un modelo de video Seedance, `content[].role` selecciona la operación (una imagen de primer fotograma selecciona imagen a video, y una imagen o un clip de referencia seleccionan referencia a video). En el despacho nativo, la facturación de Seedance sigue los tipos de medios de `content`, no los roles: una solicitud con cualquier entrada de video se factura como video a video; si no, una con cualquier imagen se factura como imagen a video; si no, texto a video, salvo que un render final de un elemento `draft_task` se factura como la operación del Draft que renderiza; algunos modelos cobran la misma tarifa por texto a video y por imagen a video. Con `model_provider` seleccionando un proveedor alternativo, cada operación condicionada puede facturarse con la tarifa propia de ese proveedor.

**Calcula el precio de una llamada a un modelo antes de ejecutarla, sin ejecutarla.**

Devuelve una estimación previa, en dólares estadounidenses, de lo que costará ejecutar este body en este modelo, con el precio de la misma tarifa contra la que se factura la ejecución (un modelo que se factura por el costo que reporta su proveedor se estima a partir de la lista de precios publicada por el proveedor). Es una estimación, no el cargo final: lo que pagas es el cargo liquidado en los registros de uso y facturación de tu espacio de trabajo. Primero se valida el body contra el esquema de entrada del modelo, tal como lo valida una ejecución predeterminada (sin `strict_mode` ni `reject_unknown_fields`), así que un body que no cumple el esquema del modelo produce el mismo `422` aquí que en la ejecución; no se despacha nada a un proveedor y no se cobra nada. La respuesta no es un bloqueo de precio: se cotiza con las tarifas vigentes en `pricing_as_of`, y una ejecución se cobra con las tarifas vigentes cuando se tarifica. Mientras la función se está implementando gradualmente, la ruta responde `403` con `error_type: not_enabled`; un modelo que Router aún no puede ejecutar responde el mismo `403` con el `detail` propio de la ruta de ejecución, así que lee `detail` para distinguir ambos casos.

**Cuerpo de la solicitud**

`application/json` -- [`RouterModelInput`](#routermodelinput) (requerido)

La entrada JSON nativa del modelo del socio, idéntica al cuerpo que la ruta síncrona acepta para este modelo, y que selecciona la operación y se factura de la misma manera: los propios campos del cuerpo eligen qué operación ejecuta Router en un modelo que admite más de una (una imagen de entrada cambia un modelo de imagen editable a imagen a imagen, que puede facturarse a su propia tarifa; una imagen de primer fotograma de Seedance selecciona imagen a video y una imagen o un clip de referencia selecciona referencia a video). El mismo contrato de selección de proveedor se aplica en el despacho: sin `model_provider`, o con `model_provider` y `strict_mode=false` (el valor predeterminado), el cuerpo es el documento nativo del modelo y se valida contra el esquema de entrada propio del modelo antes de admitir la ejecución, así que un cuerpo que el modelo rechazaría es un `422` aquí en lugar de una solicitud en cola que falla minutos después; un cuerpo no estricto de proveedor alternativo además se traduce al esquema real de ese proveedor en el despacho. Con `strict_mode=true` el cuerpo ya debe ser el esquema propio del proveedor alternativo y se reenvía sin cambios: la validación del esquema nativo se omite, exactamente como en la ruta síncrona (consulta `model_provider` y `strict_mode`).

## Categorías de error

Categoría de error del Router legible por máquina, que también se envía en el encabezado `X-Comfy-Error-Type`.

### Categorías a nivel de solicitud

Se generan cuando el Router aceptó una solicitud y después no pudo completarla.

| `error_type` | Significado |
| --- | --- |
| `invalid_input` | La solicitud se rechazó antes de llegar al modelo: un cuerpo mal formado, un cursor de paginación mal formado o vencido, una entrada que el propio esquema del modelo no acepta, o un `Idempotency-Key` que no puede servir a esta solicitud (ya usado para una solicitud diferente, porque difieren el método, la ruta y la consulta, o el cuerpo; o ya consumido por una llamada cuya respuesta no se puede reproducir). |
| `content_policy_violation` | El proveedor rechazó la solicitud por motivos de política de contenido. |
| `provider_error` | El proveedor socio informó un fallo propio, o devolvió una respuesta que Router no pudo interpretar como resultado. |
| `provider_timeout` | El proveedor socio no respondió dentro de su plazo. |
| `insufficient_credits` | El espacio de trabajo que llama no tiene créditos suficientes para ejecutar el modelo. |
| `model_not_found` | El ID `{provider}/{model}` no identifica ningún modelo que Router pueda ejecutar: un proveedor desconocido, un id no inscrito, uno que el catálogo ya retiró después de su fecha de retiro, o un ID catalogado que el proveedor no sirve actualmente para Comfy. |

### Categorías a nivel de transporte

Las genera el propio Router, antes de la llamada al modelo o en torno a ella.

| `error_type` | Significado |
| --- | --- |
| `unauthorized` | La solicitud no llevaba ninguna credencial utilizable. |
| `forbidden` | La credencial es válida, pero no tiene derecho a este modelo ni a esta operación. |
| `concurrency_limit_exceeded` | El espacio de trabajo ya tiene tantas llamadas en curso como se le permite; reintenta cuando termine una de ellas. |
| `client_disconnected` | Quien llama cerró la conexión antes de que Router pudiera devolver un resultado. |
| `internal_error` | El propio Router falló. |
| `deadline_exceeded` | Comfy dejó de mantener la conexión en su propio límite configurado antes de que llegara una respuesta. |
| `not_enabled` | Comfy Router aún no está activado para quien llama. |

## Estimaciones de costos previas a la ejecución

`POST /v2/models/{provider}/{model}/estimate` tarifica un cuerpo sin ejecutarlo, y un envío en cola (`POST /v2/models/{provider}/{model}/requests`) devuelve el mismo [`RouterCostEstimate`](#routercostestimate) que `estimate` en su `201`. Ambos se tarifican con la tarjeta de tarifas contra la que Comfy factura la ejecución, excepto un modelo que se factura por el costo que reporta su proveedor, que se calcula como `estimated` a partir de la lista de precios publicada por el proveedor. Toda cifra que devuelve cualquiera de los dos es una estimación, no el cargo final: el cargo liquidado en los registros de uso y facturación de tu espacio de trabajo es el definitivo. Comfy no factura una ejecución hecha con tu propia clave de proveedor (ver abajo). Mientras la estimación se está implementando, la ruta responde `403` con `error_type: not_enabled` y la respuesta del envío omite `estimate`. El catálogo sigue sin mostrar precios.

Lee `source` antes de cualquier cantidad. Una cifra faltante nunca significa que sea gratis.

| `source` | Contiene | Cómo leerlo |
| --- | --- | --- |
| `exact` | `amount`, `amount_cents`, `credits` | Una estimación igual al cargo de este cuerpo con las tarifas de `pricing_as_of`; el cargo liquidado en los registros de uso y facturación de tu espacio de trabajo es el definitivo. |
| `estimated` | `min_amount`, `max_amount` y sus formas `_cents`, sin `amount` | Una estimación cuyo cargo depende de una cantidad que el proveedor reporta de vuelta y que el cuerpo acota; se espera que el cargo esté entre esos límites, y el cargo liquidado en los registros de uso y facturación de tu espacio de trabajo es el definitivo. |
| `free` | `amount` "0", `amount_cents` y `credits` `0` | La tarjeta de tarifas valora esta solicitud en cero, así que la estimación es `0`; el cargo liquidado en los registros de uso y facturación de tu espacio de trabajo es el definitivo. Solo una cotización `free` se lee como `0`. |
| `unknown` | `reason`, sin cifra | No se pudo dar un precio antes de la ejecución. Trata cualquier otro valor de `source` como `unknown`. |

El `reason` de una estimación `unknown` es uno de los siguientes:

- `not_quotable`: Router no puede tarificar esta llamada antes de que se ejecute, porque se factura según una cantidad que el proveedor reporta de vuelta y que el cuerpo no acota, o porque no se puede tarificar el cuerpo tal como se envió. Trata cualquier `reason` no reconocido como `not_quotable`.
- `unpriced_model`: la tarjeta de tarifas no tarifica esta solicitud.
- `byok` (solo envío en cola): la ejecución usa tu propia clave de proveedor, por lo que Comfy no cobra nada por ella.
- `pricing_unavailable` (solo envío en cola): no se pudo leer la tarjeta de tarifas cuando se admitió la solicitud. El envío se acepta igualmente y la ejecución se cobra como de costumbre.

Los modelos para los que Router aún no puede calcular un precio antes de una ejecución se enumeran en [modelos sin una estimación previa a la ejecución](/es/development/comfy-router/limitations#modelos-sin-estimación-previa). Un modelo que no aparezca allí puede responder igualmente `unknown` para un cuerpo concreto, así que lee `source` en cada estimación.

Cuándo la estimación falla de forma segura:

- Cuando una cifra necesita la tarjeta de tarifas y la tarjeta no está cargada o está desactualizada, `/estimate` responde `503` en lugar de adivinar. Router nunca rechaza el envío en cola por su estimación; en su lugar, este lleva `source: unknown` con `reason: pricing_unavailable`. Router responde a una llamada que no se puede tarificar antes de ejecutarse en absoluto (`not_quotable`), o a un envío en cola con tu propia clave de proveedor (`byok`), sin leer la tarjeta, así que ese `200` no dice nada sobre si la tarjeta está actualizada.
- `/estimate` valida el cuerpo con el esquema de entrada propio del modelo igual que lo hace una ejecución predeterminada, así que un cuerpo que no cumple el esquema del modelo recibe el mismo `422`, con la misma forma de `detail[]`, que respondería la ejecución. No se calcula ningún precio ni se despacha nada.
- Una repetición idempotente de un envío en cola (`Idempotent-Replayed: true`) omite `estimate`, porque la cotización original no se almacena.

Límites de la estimación. Una cifra de `200` no garantiza que la ejecución se acepte ni que se cobre exactamente eso:

- `/estimate` no acepta `strict_mode` ni `reject_unknown_fields`, así que solo comprueba el contrato nativo del modelo: un cuerpo que una ejecución con `strict_mode=true` acepta en el esquema propio del proveedor alternativo puede recibir aquí un `422`, y aquí se calcula el precio de un campo de nivel superior no declarado que una ejecución con `reject_unknown_fields=true` rechazaría. Un modelo de Anthropic Messages es la excepción: su esquema permite campos no declarados, así que una ejecución con `reject_unknown_fields=true` no rechaza ninguno, y la estimación solo calcula el precio de los campos de nivel superior no declarados `tools`, `tool_choice`, `temperature`, `top_p`, `top_k`, `stop_sequences`, `metadata`, `thinking` y un `mcp_servers` vacío. Cualquier otro campo de nivel superior no declarado hace que responda `unknown` con `reason: not_quotable`.
- `pricing_as_of` indica cuándo se obtuvo la tarjeta de tarifas. Una cotización `estimated` tomada de la lista de precios publicada por el proveedor lleva la fecha en que se leyó esa lista. Una cotización `exact` o `estimated` cuya cantidad facturada se predice a partir de un calendario publicado por el proveedor lleva la fecha de lectura de ese calendario cuando es anterior a la de la tarjeta. Cuando no se leyó ni la tarjeta ni un calendario, es el momento en que se respondió la estimación. No es un bloqueo de precio: la ejecución se cobra con las tarifas vigentes cuando se tarifica.
- `/estimate` cotiza el tramo que indica `model_provider`, o el proveedor nativo. No acepta el parámetro `fallback_provider` ni `strict_mode`. Una ejecución síncrona cuyo reintento de respaldo recae en otro proveedor se cobra con la tarifa de ese proveedor, que la estimación no cotizó; `X-Comfy-Router-Fallback-Provider` en la respuesta de la ejecución indica que ocurrió. Un envío en cola no tiene respaldo, así que su `estimate` cotiza el tramo que se ejecuta.
- `/estimate` y el `estimate` de un envío en cola pueden calcular el precio de documentos ligeramente distintos para el mismo cuerpo en un tramo de `model_provider`, o para un cuerpo que se ejecuta en una operación hermana. El `estimate` del envío se calcula sobre el documento que envía la ejecución.
- `/estimate` siempre cotiza el cargo de la plataforma. Comfy no factura una ejecución con tu propia clave de proveedor, pero `/estimate` no lo detecta y aun así devuelve una cifra; solo un envío en cola responde `reason: byok`.- Los dólares se muestran a partir de centavos sin redondear, con hasta 8 decimales, y una `amount` cobrable inferior a un centavo nunca se muestra como `0`. `credits` es `round(amount × 211, 2)`, la misma conversión que `X-Comfy-Credits-Used` aplica a un cargo, así que `credits` puede redondearse a `0` para un precio muy pequeño distinto de cero; cuando eso importe, presupuesta con `amount` o `amount_cents`, no con `credits`. Ese encabezado sigue siendo la cifra posterior a una ejecución; los saldos están en la plataforma de Comfy.

## Recursos del resultado

Un modelo puede devolver URL de recursos, bytes en línea o ambos. Los proveedores siguientes copian los recursos seleccionados en el almacenamiento de Comfy y sustituyen sus URL. Este comportamiento depende del modelo; no hay ningún encabezado de solicitud que lo seleccione.

| Modelos | Qué se copia en el almacenamiento de Comfy | Tiempo de vida máximo de la URL alojada en Comfy |
| --- | --- | --- |
| `bfl/*` | el recurso finalizado, y el recurso de caché de borrador cuando el resultado lo incluye | 24 horas |
| modelos de video `byteplus/*` (`seedance`, `dreamina-seedance`) | el video finalizado, y la imagen del último fotograma cuando el resultado la incluye | 24 horas |
| `minimax/*` | el video finalizado | 12 horas |
| `xai/*` | cada imagen generada, y el video finalizado | 24 horas |

Estos tiempos de vida empiezan cuando se firma la URL, no cuando la abres. Las URL en caché o de una llamada repetida pueden tener menos tiempo restante; repetirlas no las renueva. Un registro de `Idempotency-Key` puede sobrevivir a las URL que contiene, así que desde una hora antes de que expire una de esas URL, un reintento con la misma clave recibe `409 invalid_input` en lugar de la respuesta grabada; una respuesta que ya estaba tan cerca de expirar cuando se sirvió sigue siendo repetible durante 5 minutos. Descarga el recurso cuanto antes. Solo se copian los recursos indicados en cada fila: las imágenes `byteplus/seedream-*` y `byteplus/seededit-*` no están cubiertas por la fila de video de BytePlus.

La copia la realiza únicamente el proveedor nativo del modelo. Una ejecución atendida por un proveedor alternativo (`model_provider` que nombre uno, o una ejecución nativa cuyo reintento de respaldo haya recaído en uno, indicado por `X-Comfy-Router-Fallback-Provider`) devuelve las URL propias de ese proveedor, que siguen la caducidad del proveedor y no se copian. Los valores `default`, `comfy` y `comfyui` de `model_provider` no nombran ningún proveedor alternativo, por lo que esas ejecuciones son nativas y se copian como se describe arriba, igual que una ejecución con `model_provider` cuyo reintento de respaldo haya vuelto a recaer en el proveedor nativo.

**Veo (`veo/*`) tiene una ruta de almacenamiento aparte.** En `response.videos[]`, lee el miembro que esté presente: `bytesBase64Encoded` contiene el clip en línea, mientras que `gcsUri` contiene un enlace HTTPS firmado por Comfy cuando el entorno está configurado para que el proveedor escriba directamente en el almacenamiento de Comfy. Ese enlace es válido durante 24 horas desde la respuesta. En este último caso el recurso se escribe directamente en lugar de copiarse, por lo que Veo no figura en la tabla de realojamiento.

Otros modelos devuelven referencias a recursos del proveedor o bytes en línea. Las URL del proveedor siguen la caducidad del proveedor, que puede ser mucho más corta que los tiempos de vida anteriores y no está especificada por el contrato del Router.

**URL originales de BytePlus (Seedance 2.x, opcional).** Para un espacio de trabajo en el que Comfy haya habilitado esta opción en el servidor, un resultado de Seedance 2.x también incluye las URL propias de BytePlus en `content.upstream_video_url` y `content.upstream_last_frame_url`, junto a las copiadas, además de `content.upstream_expires_at`. No hay ningún parámetro de solicitud y ningún espacio de trabajo está habilitado por defecto. Estas URL expiran 24 horas después de la generación y desaparecen una vez que BytePlus las borra; en Seedance 2.5, BytePlus limita cada una a 100 descargas, y la copia propia del Router consume una. Cada una es una credencial al portador para su objeto: cualquiera que la tenga puede descargar el recurso hasta que expire.

La copia se realiza con el mejor esfuerzo en cada recurso. Si una copia falla, esa entrada conserva su referencia del proveedor; la respuesta puede contener tanto URL de Comfy como del proveedor, sin un campo explícito de estado de copia por recurso. La generación se completa igualmente y se cobra. No deduzcas el tiempo de vida de todas las URL a partir de un recurso realojado con éxito.

Que un resultado esté alojado en Comfy también determina si más tarde aún es posible repetir una llamada completada desde su registro de `Idempotency-Key`; el parámetro `Idempotency-Key` de arriba indica qué recibe un reintento cuando no es posible.

## Esquema de entrada y salida por modelo

Lee los campos de cada modelo desde `GET /v2/models/{provider}/{model}/openapi.json`. Esa llamada requiere una clave API. El mismo documento, para cada modelo con un esquema definido explícitamente, también se publica en este sitio sin clave, en `/router-schemas/{provider}/{model}.json`. Esa copia es una instantánea tomada en la última actualización de la documentación, así que el endpoint es la fuente autoritativa cuando hay diferencias. El `requestBody` de la operación describe la validación de la entrada; su respuesta `200` describe la forma de la salida y el tipo de medio cuando este está definido explícitamente. Cuando `x-comfy-input-schema-authored` es `false`, Router acepta cualquier objeto JSON sin prevalidación específica del modelo. Los requisitos del proveedor siguen aplicando. Los esquemas de salida describen resultados; Router no valida contra ellos las cargas útiles que devuelve el proveedor. Una salida sin esquema definido explícitamente puede usar `*/*` en lugar de `application/json`; revisa el tipo de contenido de la respuesta antes de decodificarla.
